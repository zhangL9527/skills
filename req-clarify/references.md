# 细则：事实抽取 · 影响面盘点 · 实现方案写作标准

> SKILL.md 是骨架，本文是三处最吃细节的展开。按需查，不必每次通读。
> 所有 `file:line` 指向 Stage 0 锁定的基线目录，不是工作区。

---

## 一、代码事实抽取方法（Stage 1 细则）

### 通用原则

1. **先定作用域，再抽事实。** 作用域 = 本次需求改动的页面/模块/接口/服务，由方案条目圈定。范围外的事实抽到也不上报。
2. **沿"调用链"抽，不要沿"目录"抽。** 从方案提到的入口出发顺调用链往下走；走到**共享的查询/写入入口**（多个入口共用的 service/mapper/查询构造器）时停下来横向展开 —— 共享入口是遗漏高发区。
3. **抽"行为"不抽"名字"。** 老代码里 `getXxx` 可能是删操作，以实际读写了什么为准。
4. **每条事实必须能被单点验证。** "五个按钮共用一个查询"要能指到具体行。
5. **要全集不要抽样。** 抽样是遗漏类缺陷漏检的头号原因。

### 六类事实：抽什么、怎么找

| 类别 | 抽什么 | 检索模式 |
|---|---|---|
| **入口事实** | 按钮/菜单/Tab/路由/API 端点：触发动作、权限点、**最终落到哪个共享查询入口** | 前端路由表、事件绑定；后端 Controller 的 RequestMapping；从入口顺调用链到 service/mapper |
| **类型事实** | 枚举、类型码、字典表、type 字段的全部取值及各取值的行为差异 | enum 定义、字典表数据、按类型码 switch/分支的地方 |
| **字段事实** | 表结构全量字段、DTO 字段、每个字段的写入点与取值来源 | schema/migration 文件、实体类、INSERT/UPDATE 语句 |
| **流程事实** | 状态机（状态枚举 + 流转条件）、时序、异步任务/定时任务 | 状态枚举 + 状态流转代码、job/MQ listener/回调 |
| **约束事实** | 校验规则、唯一性约束、前置条件、权限限制 | validate 注解、if guard、数据库唯一索引、权限码 |
| **副作用事实** | 写操作连带触发的非主表动作：统计累计、消息推送、缓存失效、日志、下游同步 | 写方法体内主表写入之外的其它调用 |

## 二、影响面盘点方法（Stage 2 细则）

新增一个类型/入口/字段/状态/规则，不是"加一个东西"，而是给系统加了**新的分流维度** —— 凡按它分流、或受它影响的存量功能都要表态。产品最常犯的错不是"改错了"，而是"**没想到要改**"。

### 三条硬规则

1. **清单由代码生成。** 每条盘点项必须带 `file:line`，没证据的不要列。
2. **"不受影响"也要显式表态。** 结论是不改，同样要有理由（file:line）—— 它是免责证据，让产品能看到并能反驳。写进实现方案的「存量功能结论落地对照」。
3. **疑点要有解法。** 每条方案遗漏必须给「现状行为 → 可选解读 → 建议默认」。开放式提问是澄清失败的主因。

### 同一根因必须合并

五个老按钮共用一个查询入口 → 盘点底稿里是**一行**，不是五行。产品一次回答能覆盖的才叫盘点。

### 七维度各自的枚举法

| 维度 | 枚举问题 | 怎么扫 |
|---|---|---|
| ① 数据可见性 | 哪些列表/查询/搜索/导出/报表会看到新数据？ | 找**共享查询入口**：新数据写入的表被哪些查询读，顺着 mapper/查询构造器反查入口 |
| ② 行为分流 | 哪些 switch/if/策略选择按该维度分流？新数据落进哪个分支？ | 全局搜类型码/状态值，列出每个分流点 |
| ③ 字段与校验 | 哪些表/DTO 要加字段？哪些既有校验对新数据不适配？ | 字段事实 + 约束事实交叉 |
| ④ 副作用 | 新增写入会连带触发什么？统计要不要累计？推送/缓存要不要处理？ | 写入口的副作用事实 |
| ⑤ 流程与时效 | 新数据走不走现有流程节点/定时任务？时效规则适用吗？ | 流程事实：新数据进入状态机后，哪些节点会处理它 |
| ⑥ 对外与集成 | 对外 API/回调/消息契约要不要变？第三方能感知吗？ | 副作用事实 + 对外接口清单 |
| ⑦ 权限与配置 | 新东西归哪个角色管？要不要新权限码/配置项/菜单挂载？ | 权限点事实 + 配置读取点 |

逐维度问「新增的这批数据要不要影响它」：有疑点 → 方案遗漏；确定不受影响 → 对话内留痕（一句理由 + `file:line`）。

## 三、实现方案写作硬标准（Stage 6 细则）

**第一读者是 AI 编码代理。** 它不会停下问"这个字段为空怎么办" —— 会选一个"最合理的默认值"继续写，产出看起来对但不对的代码。**方案里省下的一句话，会变成下游的一次猜测。** 但本文档仍不产出代码：给改动指令与关键片段，不给完整实现。

### 必须写到（缺一项 = 下游多一次猜测）

1. **变更点**：文件 + `file:line` + **锚点方法名**（行号会漂，方法名是稳定锚）+ 可照抄的改法（改成什么样，关键片段）。
2. **类名/方法名**：新增的类、方法、常量的完整命名，AI 不许自己起名。
3. **DDL**：新表/改表的完整建表语句；新字段的类型、默认值、注释、索引。
4. **枚举取值**：新增枚举值的全集（含展示名），以及它落库的值。
5. **接口契约**：路径、方法、入参出参结构、错误码、幂等/分页等行为约定。
6. **流程步骤与失败处理**：主流程每步 + 每个可能失败点的处理（重试/回滚/提示）。
7. **不做清单**：明确写出本次不改什么 —— 防止 AI 顺手"优化"。
8. **术语表**：术语 ↔ 定义 ↔ 代码标识 + **禁止的其它写法**（同一概念多个叫法会被 AI 当成两个东西，造出两套实现）。
9. **逐条验收标准**：每条可独立执行验证（给定输入 → 期望输出），覆盖每条业务口径。
10. **存量功能结论落地对照表**：每条上轮方案遗漏、每条「无需调整」，都要有落点（改了什么/沿用现有什么）—— 没落点 = 盘点白做。

### 业务口径不能丢

不要因为"要写实现"就把业务口径丢了。"退款金额不得超过原单实付"这种规则，即使代码里是 `if (amount > origin.payAmount) throw`，也必须**先用业务语言写一遍** —— 否则 AI 换个方向实现，业务就错了。

### 交付前检查清单（逐项打勾）

- [ ] 零 `TBD`/占位符残留
- [ ] 每个变更点有：文件 + 行号 + 锚点方法名 + 改法
- [ ] DDL 与字段级描述一致（无字段只在一边出现）
- [ ] 新增类/方法/枚举命名完整，无"自行命名"空间
- [ ] 每条接口契约含错误处理
- [ ] 每条业务口径都有对应验收标准
- [ ] 不做清单非空（至少列出确认不动的相邻功能）
- [ ] 术语表含"禁止的其它写法"
- [ ] 上轮每条疑点/遗漏在「存量功能结论落地对照」有落点
- [ ] 头部两行写了双端基线分支与提交
