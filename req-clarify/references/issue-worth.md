# 提问价值自检（Issue Worth）

> **产出问题 ≠ 产出好问题。** 覆盖矩阵和七维度扫描保证**不漏**，但它们**不保证每一条都值得占用产品的注意力**。
> 一份掺了 5 条"产品答不了 / 答案早已确定"的问题清单，会让产品对**整份文档**的可信度打折 —— 他分不清哪条是真缺陷、哪条是凑数。
> 所以在"把疑点写成问题"之前，必须先过这一关。

## 为什么必须有这一步（真实翻车样本）

某轮问题清单产出 19 条，复盘后：

| 处置 | 条数 | 典型 |
|---|---|---|
| 保留 | 12 | 操作后单据的去留、弹窗字段能否改、批量能力是取消还是保留 |
| 改写 | 3 | “多个候选项按什么顺序取第一个” → 只问“候选范围 + 一个都没有时怎么办” |
| 合并 | 1 | “方案里某条已实现的需求这次还要改什么” + “某章是空的” → 合并成一条「方案待补写」 |
| 丢弃 | 5 | 见下表 |

被丢弃的 5 条的共性 —— **它们都不是"方案有歧义"，而是"答案早已由代码/事实决定"或"产品拍不了"**：

| 丢弃的问题 | 为什么丢 | 正确的去处 |
|---|---|---|
| 操作后「关联状态」按什么规则重算 | 整单操作 → 已生成量被整额扣回 0 → 按既有重算规则必然落回“未生成”。**代码决定的，不是业务选择** | 开发说明（方案里写一句“沿用现有操作的重算规则”） |
| 主单自身状态要不要复位 | 能被操作的单前置条件就是“未推送下游”，复位与否无差别；现有同类动作也都不复位。**建议默认 = 现状 = 零信息量** | 但要把它下面的**真问题**捞出来：前置条件缺“单据状态” → 改写成新问题 |
| 这次操作要不要写操作日志 | 现状**本来就没有**日志（只有明细上的更新人+时间）。要审计属单独立项 | 「给开发」备注 |
| 明细导出要不要体现这次操作 | 操作语义就是“回到初始态”，导出取当前值是自然结果 | 不需要问 |
| 扫进来的数据记哪个归属方 | 不改代码的自然行为就是“照实记它自己的归属”，**产品没有第三个选项** | 方案里的**风险提示**，不是提问 |

> 共同教训：**"建议默认"等于"维持现状"的问题，问了也是白问** —— 它把额度花在产品答不出"要"的题上。

## 四道闸门（逐条过，任一关不过就不能作为编号问题）

### 闸门 ① · 产品拍得了吗？

产品能拍板的是**业务规则**：流程走向、字段语义、可见性口径、权限范围、交互形态、数据归属的**业务**约定。

产品拍不了的是**技术实现**：

| 类别 | 例子 | 处置 |
|---|---|---|
| 排序 / 取值规则 | "多个候选仓按什么顺序取第一个" | 改成稳定排序（按编码），写进开发说明 |
| 落库位置 | "箱码存在哪张表" | 问业务口径：箱码从哪来、谁打印、什么场景 |
| 命名 | 权限码前缀、枚举常量名 | 不问，写方案里 |
| 框架 / 基建 | 日志用哪个表、要不要加审计框架 | 不问；产品只答"要不要留痕" |

> **判据**：这条问题的答案，改完之后**方案里会多出一句话业务规则**吗？不会 → 是技术细节，处置掉。

### 闸门 ② · 答案会改变方案写法吗？

- 建议默认 = **维持现状 / 不需要 / 不写** → 问了也是零信息量，**降级为「给开发」备注**。
- 建议默认 = **沿用既有代码规则**（而既有规则是确定的）→ 答案被代码锁死，**降级为开发说明**。
- 建议默认 = **照搬存量同类动作**（如"和删除/关闭一个逻辑"）→ 多数情况仍是**确认式**问题，但可降级为「中」，不必展开三个解读。

### 闸门 ③ · 答案能被另一条问题推导出来吗？

**依赖型问题不单独问。** 若 B 的答案由 A 唯一确定，问 A 就够了。

> 例："回退是整单还是部分？" 一旦答"整单"，"回退后明细状态怎么算" 就被代码规则锁死 —— 后者不该再占一条额度。

同理：**同主题合并**。留痕 / 审计 / 导出体现 这类问题，本质是同一个诉求（"要不要能看出这单被退过"），**合并成一条**（哪怕要分"页面 / 导出 / 操作日志"三个小问），不要拆成三条各占一个编号。

### 闸门 ④ · 方案原文自己能不能读出来？

方案已经写明的、或者读完方案就能得出的结论 → **不作为问题**，在「给开发」里作为**背景事实**一句带过。

## 第五道测试 · 方案改写句

> **一条合格的问题，必须能被改写成方案里的一句话。**

写法：*"产品答完这句之后，方案里要改成哪一句？"* —— 改不出来，说明这条问的不是方案，是实现。

| 合格 | 不合格 |
|---|---|
| “操作后这张单是保留还是删除？→ 方案补：操作后单据保留，状态改为『已处理』” | “这个码应该怎么设计？”（答完也不知道方案哪句话要变） |
| “多个候选时默认带出哪一个？→ 方案补：默认取编码最小的一个” | “候选的排序规则是什么？”（这是开发细节，方案不需要写） |

## 五种处置（没有"丢弃了就不管"）

丢弃一条疑点 ≠ 把它从视野里抹掉。**广度承诺要求"扫过的都要有结论"**，所以每条疑点必须有明确去处：

| 处置 | 去处 | 占产品额度？ |
|---|---|---|
| **保留** | 编号问题（Q-xxx），进汇总表 | ✅ |
| **改写** | 编号问题，但换了问法/换了对象 | ✅ |
| **合并** | 并入相邻编号问题，作为「连带影响」或同题多问 | ➖（不新增编号） |
| **降级为备注** | 相关问题的「给开发」段里写一句"现状是…，本次按…处理" | ❌ |
| **丢弃** | **在对话里留痕**（一句理由 + `file:line`），不写进交付物 | ❌ |

> **技术事实类内容（数据归属、排序、表结构、日志现状）的默认去处是「给开发」备注 / 「风险提示」，不是问题。**
>
> **交付物只留问题本身** —— 排查范围、免打扰清单、版本沿革、基线与方案路径都在对话里，不进 `问题清单.md`。

## 自查怎么落地（Stage 4.5 的动作）

1. 把 Stage 4 汇总的疑点列成一张**候选表**：候选问题 | 来源（疑点/遗漏） | 建议默认 | 建议处置。
2. 逐条过四道闸门 + 方案改写句测试，标注处置。
3. **合并同主题**：留痕类、导出类、权限类、状态类 —— 每个主题最多一条。
4. **剔除依赖型**：能被别的答案推导出来的，删。
5. 定稿后把候选表与最终清单的差异写成**一段自查说明**（对话里给使用者，不必进产品文档）：
   > 本轮候选 24 条 → 交付 13 条。删 6 条（产品拍不了 3 / 答案=现状 2 / 技术事实 1），改写 3 条，合并 2 条。
6. **额度控制**：面向产品的清单建议 **≤ 15 条**（硬上限 ~20）。超了先合并同主题，再砍低级别 —— 但**不要砍高价值问题去凑数，也不要保留凑数问题**。

## 常见误判（自查时对照）

| 误判 | 正解 |
|---|---|
| "导出要不要体现？" —— 凡是涉及导出都要问一遍 | 只有当"导出与页面口径不同"或"需要留历史痕迹"时才问；导出天然取当前值 → 不问 |
| "要不要写日志？" —— 所有新增操作都要留痕 | 只在**产品/合规**明确在意时问；现状没有 → 降级为备注 |
| "字段默认值怎么取？" —— 所有字段都要问 | 现有代码已有默认值且语义不冲突 → 不问，写进开发说明 |
| "权限点怎么命名？" | 不问。产品只答"谁能点"，命名写方案里 |
| "多个候选取哪个？" | 排序不问；但"**多个候选取不到 / 兜底**"要问（那是业务兜底） |
| "要不要加个状态标记？" | 若状态语义已在方案里定义 → 不问；若要新增字段/枚举 → 问 |
