# 质量门（Gate）

每一门是一组**可机械检查**的放行条件。门未过，不得进入下一阶段。

带着未澄清项进入 Stage 6，等于把歧义直接喂给编码代理 —— 它不会提问（人靠猜，AI 靠"最合理的默认值"），悄悄填上，最终产出"看起来对但不对"的代码。

---

## G0 · 输入可解析（Stage 0 后）

| 检查项 | 放行条件 |
|---|---|
| **输入引导** | 三项必填输入（① 项目地址：后端+前端仓库根；② 方案地址/路径；③ 取证分支：后端+前端）已收齐，且六项最终值（方案地址、后端路径、前端路径、后端分支、前端分支、产物目录）已回显给使用者确认。**已给过的值不再问** —— 参数 / 对话已说过的直接采用并标来源 |
| 条目编号 | 每条需求有唯一 ID `REQ-xxx` |
| 改动对象 | 每条需求明确指出改什么（页面/接口/表/枚举/流程） |
| 目标 | 每条需求说明改完达到什么效果 |
| 作用域 | 已圈定受影响的模块/页面/接口清单 |
| **迭代夹** | 已建夹：单夹 `<方案名> 迭代/`（无轮次后缀，每轮覆盖）。扫描 `<产物目录>/` 下是否已有该夹：有 → 本轮覆盖；无 → 新建。**不再有 `迭代1/迭代2/迭代3` 这类轮次后缀**。同轮续跑复用已有夹，不新建；产品提交新方案才覆盖（版本号在 `问题清单.md` 内部 +1）；`产品方案/`（方案原文+原型，**保留原始文件名**）已落盘 |
| **代码库** | 后端、前端路径**均经使用者确认**（默认值 = 当前终端目录，未经确认不生效；标「无」的一端跳过）；已验证存在、可读、是 git 仓库根、确实是代码库（不是空目录 / 不是代码库）。**不合格只重问该项**，并说清「哪一项不合格 + 实测结果」 |
| **代码基线** | 后端/前端分支各自锁定 —— 默认 `master`（该仓无则 `main`），**由使用者确认**，可显式指定当前工作区分支（须已告知「未提交改动不进基线」的险）；两端各跑 `prepare-baseline.sh`，快照落在**基线根目录**（默认 `${TMPDIR:-/tmp}/req-clarify-baseline`，不在产物目录里）；**两端分支+提交号分两行记录**；若某端降级到工作区（无 master/main）或基线不完整（源文件未被跟踪），**已分端如实告知使用者**；同一 `(repo, 分支, 提交)` 自动复用（降级情形不复用） |
| **新增物种类** | 已判定为 类型/入口/字段/状态/规则/角色/渠道/配置 之一（决定 Stage 2 重点维度） |
| 术语归一 | 方案中同一概念的多种写法已列出（供 C2 检查） |

**不通过的处理**：输入缺失就回到 **Stage -1 输入引导**（`references/input-collect.md`），不要自行假定；**只重问真正缺的那一项**，已给过的值直接采用；方案零散时，按"改动对象"重组成条目；方案缺目标描述的，直接列为澄清问题，不要自己脑补。代码库缺失或无效时，**停下来问用户**，不要对着空目录编出一份"完整"的问题单。**基线锁不住时也不许将就** —— 至少要让使用者知道"本次证据取自工作区现状，不是主干代码"。

## G1 · 事实完备（Stage 1 后）

| 检查项 | 放行条件 |
|---|---|
| 六类事实 | 入口/类型/字段/流程/约束/副作用**均已抽取**（允许某类为"无"，但要显式声明已查过） |
| 全集声明 | 枚举列出全部取值；字段列出完整列集合；流程列出全部状态节点 |
| 证据完备 | 每条事实有 `file:line` |
| 共享入口标注 | 每个入口事实标注了它最终落到的共享查询/写入入口 |
| 差异化分支 | 每个类型取值都追了差异化处理位置 |

**全集 vs 抽样的区别**：
- ❌ "找到 3 个按钮" —— 抽样
- ✅ "该页面共 5 个按钮，逐个列出" —— 全集

抽样会让"老入口遗漏"这类缺陷系统性漏检。

---

## G1b · 扫描无盲区（Stage 4 后，随疑点落盘）

| 检查项 | 放行条件 |
|---|---|
| 七维度覆盖 | ①数据可见性 ②行为分流 ③字段与校验 ④副作用 ⑤流程与时效 ⑥对外与集成 ⑦权限与配置 —— **七项均已扫过** |
| 全集声明 | 每个维度下有"已扫过，确认无其它"的声明 |
| 证据完备 | 每条扫描项有 `file:line` |
| 根因合并 | 共享同一入口/分支的存量功能合并为**一项**，不是多项 |
| 两端都有结论 | 每条扫描项都有明确结论：「需澄清」（转成疑点）或「无需调整」（带理由）—— 不允许悬空 |
| 重点维度 | 新增物种类的重点维度（见 `impact-inventory.md`）已逐项表态 |

**这一门保证「广度」。** 只挑"我怀疑有问题的"几个点来问 —— 产品无法判断你漏了什么，问题单就退化成零散追问。**七维度全量扫完**，且**「无需调整」的也要写进清单** —— 产品自己看出"哦，导出和统计我没想到"，也能看出"这几处你们查过了，结论是不用改"。

## G2 · 覆盖无空洞（Stage 3 后）

| 检查项 | 放行条件 |
|---|---|
| 零空格 | 矩阵中**不存在**未填的格子 |
| 三态标注 | 每格是 `✔` / `✘`(带理由) / `?`(带问题单编号) |
| 问题单映射 | 每个 `?` 都能在问题单里找到对应条目 |
| 作用域已判 | 每个 `?` 事前已通过作用域判定（非误报） |

**零空格是硬门。** 允许"待澄清"（`?`），不允许"没人看过"（空格）。空格 = 事实抽取漏了。

---

## G3 · 矛盾清零（Stage 4 后）

| 检查项 | 放行条件 |
|---|---|
| 冲突对清零 | 每对冲突都在**方案里被修正**（改稿后重扫矩阵，冲突格消失） |
| 修正可追溯 | 改稿要点写进 `问题清单.md` 的版本记录段，含问题 ID + 冲突描述 + 改法 |
| 无悬空命名 | 术语表中每个概念只有一个规范写法 |
| 重扫无新增 | 改稿后重跑矩阵，无新增冲突格 |

**修正必须落进版本记录，不能只在对话里说。** 版本记录的作用是防止同一问题反复问，也防止实现方案与方案原文打架。

---

## G4 · 属性完备（Stage 4 后）

| 检查项 | 放行条件 |
|---|---|
| 无半填格 | 每个"已覆盖"的字段格，取值/默认值/何时写 三项齐全 |
| 对象齐全 | 关联对象清单完整，无"主要对象讲了、附属对象没讲" |
| 分支齐全 | 枚举每个取值的处理方式都有交代（含"沿用现有行为"的显式声明） |
| 默认值明确 | 方案未提但代码有默认值的字段，明确"沿用"还是"改" |
| 边界明确 | 字段为空/缺失时的行为有定义 |

**"沿用现有行为"必须写出来。** 方案不说，AI 就会自己选一个默认 —— 通常是它认为最合理的那���，通常不是你要的。

## G5 · 流程等价（Stage 4 后）

| 检查项 | 放行条件 |
|---|---|
| 节点映射 | 现状每个状态节点都能在方案中找到对应（或被显式声明为不涉及） |
| 边映射 | 现状每条流转都能在方案中找到对应 |
| 静默节点 | 现状所有"不改状态但有副作用"的节点已逐个确认 |
| 三要素 | 每条边都有触发条件 + 守卫条件 + 副作用 |
| 异常路径 | 超时 / 拒绝 / 撤销 / 并发重复 的处理有定义 |
| 差异已说明 | 方案新增的节点/边已说明插入位置 |

## G8 · 提问价值（Stage 4.5 后，路径 A 专属）

> 覆盖矩阵与七维度扫描保证**不漏**；G8 保证**每条都值得占用产品的注意力**。
> 掺一条"产品答不了 / 答案早已确定"的问题，产品就会对**整份文档**的可信度打折 —— 他分不清哪条是真缺陷、哪条是凑数。

| 检查项 | 放行条件 |
|---|---|
| 四道闸门 | 每条候选疑点都过完：①产品拍得了吗 ②答案会改变方案写法吗 ③答案能被另一条推导吗 ④方案原文能读出来吗 |
| 方案改写句 | 每条保留的问题都能回答："产品答完这句，方案里要改成哪一句？" —— 答不出来的不保留 |
| 处置完备 | 每条候选疑点都有明确处置：保留 / 改写 / 合并 / 降级为「给开发」备注 / 丢弃 |
| **丢弃留痕** | 被丢弃/降级的疑点落到「排查范围」表（确认不受影响 / 作用域外）或某条问题的「给开发」备注里 —— **不占额度，但不消失** |
| 同主题合并 | 留痕 / 导出 / 权限 / 状态类主题**各自最多一条** |
| 依赖型剔除 | 答了 A 就锁死 B 的，**B 不单独成条** |
| 额度 | 清单条数 ≤ 15（硬上限 20）；超了先合并同主题，再砍低级别 —— 不砍高价值问题去凑数 |
| 自查说明 | 候选 N 条 → 交付 M 条的删/改/合差异已写成一段说明（对话里给使用者） |

## G9 · 交付物自洽（Stage 5 后，问题清单专属）

> 这些错是**人眼最容易漏、读者却一眼就发现**的：说 19 条其实 18 条、合计 20 处但只列 18 条、基线提交号写成了另一个分支的。一处错就足以让产品怀疑整份文档的严谨度。

| 检查项 | 放行条件 |
|---|---|
| 三处计数一致 | 头部「待澄清 N 条（高 x / 中 y / 低 z）」、「怎么用」段的总数/高中级/低级数、「下一步」段的两个数字 —— **全部等于汇总表实际** |
| 版本记录 | 「本轮提疑点数」「剩余」与汇总表实际条数一致 |
| 编号连续 | Q-xxx 从 Q-001 连续编号，无重复、无跳号 |
| 排查范围自洽 | 每行「需要改」处数 == 该行「对应问题」列的 Q 条数；合计行 == 各行之和；免打扰清单条数 == 合计「确认不受影响」 |
| 交叉引用 | 全文 Q-xxx / REQ-xxx 均能在汇总表 / 需求条目表里找到；排查范围引用的 Q 必须存在 |
| 基线标识 | 头部两行写成 `路径@分支@提交`，**提交号 = 实际基线目录**（从 `prepare-baseline.sh` 输出抄，不凭记忆） |

**机器过一遍**：`bash scripts/check-issue-list.sh [--baseline <槽位目录>]... <夹>/问题清单.md` —— **零 FAIL 才算过**，WARN 逐条确认。传 `--baseline` 时会额外校验文档头部写的提交号 = 真实基线槽位。

## G6 · 文档自洽（Stage 6 后）

| 检查项 | 放行条件 |
|---|---|
| 零未决项 | 实现方案中无 `?` / `TBD` / `待确认` / `同上` |
| 零内部矛盾 | 实现方案自身无冲突；且与方案原文无冲突（除非纪要已明确改稿） |
| 零隐含假设 | 每个"未提及但必须决定"的点，都被显式写成决定或显式标为"沿用现有" |
| 有不做清单 | Out of Scope 章节存在且具体 |
| 有术语表 | 每个术语有唯一定义；全文只用术语表里的写法 |
| 口径明确 | 每条改动说清"改成什么"，无含糊表述、无"看情况" |
| 可追溯 | 方案条目 ↔ 改动项 ↔ 影响维度编号 互查得通 |
| **存量功能结论落地** | 每条方案遗漏的结论，实现方案里有对应描述；每条「无需调整」的，显式写明「沿用现有」—— 不允许因为"不用改"就整行消失 |
| 无占位代码 | 不出现 `// TODO`、`??`、`xxx` 之类占位 |

**"零隐含假设"是 G6 的核心，也是 AI 编码质量的真正决定因素。** AI 遇到空白不会停下，它会继续编。

## G7 · 可编码性（Stage 6 后）★实现方案专属

> G6 管"说得对不对"，G7 管"**说得够不够细，AI 能不能直接照着写**"。
> 两者都过了，这份文档才能交给编码代理。

| 检查项 | 放行条件 |
|---|---|
| 定位到位 | 每个改动项都有 `file:line` **+ 锚点方法名/字段名** —— 只给行号会改到隔壁方法 |
| 改法可照抄 | 每个改动项都给了代码片段或明确步骤，不是"加个判断""适配一下" |
| 枚举列全 | 所有同名枚举位置都列了（含后端多套 + 前端 `ENUM.js` 多处） |
| 表结构完整 | 有变更的给了可执行 DDL；无变更明写"本次无表结构变更" |
| 字段列全 | 字段表完整，且有"未列出的字段"说明 |
| 接口无省略 | 入参出参逐项列全，无"同上" |
| 异常分支齐 | 流程每一步都有失败处理；幂等闸门写明 |
| 定时任务全 | 给了间隔、处理逻辑、完结条件、失败策略 |
| 验收可执行 | 每条验收标准有「操作」和「预期」，且覆盖异常路径 |
| 有不做清单 | 明确列出"待沟通""后续迭代"等不得自行实现的内容 |

## 门与阶段对照

```
Stage -1 输入引导（三项：项目地址+方案地址+取证分支） ─▶ Stage 0 解析+建迭代夹+锁双基线 ─G0─▶ Stage 1 抽取（双仓各 survey，对话内）─G1─▶ Stage 2 七维度扫描（对话内） ─▶ Stage 3 矩阵（对话内） ─G2─▶
Stage 4 检查器 + 疑点定级（对话内） ─G1b/G3/G4/G5─▶ Stage 4.5 提问价值自检（候选→可交付）─G8─▶ Stage 5 放行判定 ★分支点
   ├─ 有疑点 ─▶ 产出 问题清单.md（只读，内部标版本）→ verify-citations.sh + check-issue-list.sh ─G9─▶ 产品改方案 → 复用同一夹重跑 Stage 0~4.5（基线按 commit 自动复用）
   └─ 无疑点 ─▶ Stage 6 实现方案 ─G6/G7─▶ 交付
```

**Stage 2 与 Stage 3 在每一轮改稿后都要重跑。** 一次改稿常常连带影响别处 —— 新类型的定义变了，七个维度要重扫，矩阵里所有格子也要重看。
**G1b 放在 Stage 4 之后检查** —— 七维度扫描的结论（疑点 + 无需调整清单）在这一步才落进问题清单。
**G6 与 G7 都在 Stage 6 之后检查** —— G6 管对不对，G7 管够不够细。
