# 影响面盘点（Impact Inventory）

## 为什么必须有这一步

新增一个类型 / 入口 / 字段 / 状态 / 规则，**不是"加一个东西"，而是给系统加了一个新的分流维度**。

> 凡是**对这个维度分流**、或**受这个维度影响**的存量功能，都必须表态：新东西来了，它要不要跟着变？

产品最常犯的错不是"改错了"，而是**"没想到要改"**。方案里只写新东西怎么实现，存量功能一个字不提 —— 这不是粗心，是**认知盲区**：人在设计新功能时，脑子里装的是"新功能"，装不下"我正在改的这套系统还有哪些地方会被牵连"。

所以本步骤的核心不是"再问几个问题"，而是**把"该想到什么"从人的脑子里搬出来，用代码扫出来**。扫出来的结论二选一：变成一条**方案遗漏**问产品，或写进**「无需调整」**清单说明这里查过了、结论是不受影响。

---

## 三条硬规则

1. **清单由代码生成。** 每条盘点项必须带 `file:line`。没有证据的盘点项不要列 —— 产品会当成"你在找茬"。
2. **"不受影响"也要显式写出来。** 结论是不改，同样要有理由 —— 它是免责证据。写出来不是给产品填表，是让产品**看到**并能反驳。
3. **疑点要有解法，不能只有问题。** 每条方案遗漏必须给出「现状行为 → 可选解读 → 建议默认」。开放式提问是澄清失败的主因。

---

## 同一根因必须合并成一项

> 五个老按钮共用一个查询入口 ⇒ 扫描底稿里是**一行**，不是五行。

产品一次回答能覆盖的才叫盘点。五行 = 五次回答 = 产品放弃。

---

## 七个盘点维度

新增物的种类不同，重点维度不同，但**七个维度都要扫一遍**（重点维度决定提问密度）。

### 维度 ① 数据可见性（Inclusion）

**问**：这批新数据在哪些地方**出现**、哪些地方**不该出现**？

| 盘点项 | 代码线索 |
|---|---|
| 列表页 / Tab / 筛选项 | 页面组件、`onClick`、`load(`、查询参数 |
| **导出** | `export`、`blob()`、导出模板 —— ⚠️ 导出常走**另一条 SQL**，列表过滤了导出可能没过滤 |
| 搜索 / 高级筛选 | 搜索接口、筛选参数构造 |
| 统计看板 / 报表 | `count`、`sum`、`group by`、报表服务 |
| 待办 / 工作台 | 待办列表接口 |
| 消息中心 / 站内信 | 消息查询、模板 |
| 对外查询 / 开放平台 | 公开 API、第三方查询入口 |
| **明细/详情页** | 详情路由、弹窗/抽屉组件、`detail(`、`getOne` —— ⚠️ 列表"操作"列有入口但方案没给明细页原型时极易漏 |

> **反向检查（必做）—— 产出物落点**：上表全是"新数据进哪些老入口"。还要反向问一遍：**方案声明的产出物/返回值**（如"申请条码"返回的 barCodeList、"生成回单"返回的回单号、外部系统回写的工单号/报检号）**在列表/明细/导出里有没有字段落点？** 模块名带"条码/回单/证书"却列表无该字段、用户拿不到产出物——这是最严重的纵向遗漏，横向"新数据进老入口"思维扫不出来。逐个产出物核对：存哪张表 → 列表哪一列展示 / 明细页哪一块展示 / 导出哪一列。三处全无 → 方案遗漏。

### 维度 ② 行为分流（Routing）

**问**：新数据**走哪条分支**？

| 盘点项 | 代码线索 |
|---|---|
| `switch` / `if` 分支 | `switch (...type...)`、`if (... === ...)` |
| 策略 / 映射表 | `Map<K,V>`、`Record<K,V>`、`handlers[`、策略注册 |
| 状态机 / 审批流 | `transition`、`stateMachine`、`approve`/`reject` |
| 灰度 / 白名单规则 | `whitelist`、`featureFlag`、`canary` |
| 兜底分支 | `default:` —— ⚠️ **新增类型不显式表态就会落到这里** |

> **纵向检查（必做）—— 操作入口完整性**：上表全是"数据走哪条分支"。还要逐个**操作入口/按钮**核对它背后的定义是否齐全，方案常只写按钮名不写行为：① **可选范围**——哪些状态/类型的记录能点这个按钮（状态守卫）；② **批量 vs 单条**——选中多行还是逐行；③ **入参**——前端传什么（选中 id？整行数据？）、后端补什么（登录人？系统生成号？默认日期？）；④ **目标页面**——点完跳哪、明细/详情页原型有没有。四项任一缺失 → 方案遗漏。典型漏法：方案写"申请"按钮，但没说批量还是单条、没说申请时前端传 id 还是整行、没说哪些状态可点。

### 维度 ③ 字段与校验（Field & Validation）

**问**：新增/编辑时字段怎么填？校验规则要不要变？

| 盘点项 | 代码线索 |
|---|---|
| 字段全集与赋值 | DDL、Entity、setter、builder、对象字面量 |
| 默认值 / 非空 / 唯一 | `default`、`NOT NULL`、`UNIQUE` |
| 范围与格式校验 | `validate`、`@NotNull`、`check`、`assert` |
| 业务上限（与存量数据的关系） | 跨表比较、聚合查询 |

### 维度 ④ 副作用（Side Effects）

**问**：新增时**会不会触发**这些副作用？

| 盘点项 | 代码线索 |
|---|---|
| MQ / 事件 | `publish`、`emit`、`producer`、事件总线 |
| 消息 / 邮件 / 短信 / 推送 | `notify`、`send`、`sms` |
| 日志 / 流水 / 审计 | `writeLog`、`history`、`audit` |
| 异步任务 / 定时任务 | `@Scheduled`、`cron`、job |
| **额度 / 积分 / 库存 / 优惠券** | `quota`、`stock`、`point`、`coupon` |
| 第三方调用 | HTTP 客户端、SDK 调用 |
| 对账 / 结算 | `statement`、`reconcile` |
| 缓存失效 / 下游同步 | `cache`、`sync` |

### 维度 ⑤ 流程与时效（Flow & SLA）

**问**：新数据走哪条流程？**时限变不变**？

| 盘点项 | 代码线索 |
|---|---|
| 状态集合与流转边 | `status`、`state`、`transition` |
| 超时 / 定时流转 | 超时任务、`hoursAgo` |
| 审批 / 驳回 / 回退 | `approve`、`reject`、`rollback` |
| 提醒 / 催办 | 提醒任务、消息模板 |
| 自动流转 | 状态变更的定时任务 |

### 维度 ⑥ 对外与集成（External）

**问**：对外暴露成什么样？**下游要不要适配**？

| 盘点项 | 代码线索 |
|---|---|
| 对外 API | Controller 路由、响应 DTO（含枚举字段） |
| Webhook / 回调 | `webhook`、`callback`、`notifyUrl` |
| 导出模板 / 报表格式 | 模板文件、Excel/CSV 列定义 |
| 数据同步 / ETL | 同步任务、binlog 订阅 |
| 对外文档 / SDK | 接口文档、OpenAPI |

### 维度 ⑦ 权限与配置（Access & Config）

**问**：要不要单独的**权限 / 开关 / 白名单**？

| 盘点项 | 代码线索 |
|---|---|
| 菜单 / 按钮权限码 | `permission`、`permCode`、`hasPermission` |
| 角色可见性 | `role`、`authority`、`isAdmin` |
| 租户 / 组织配置 | `tenant`、配置中心 |
| 灰度开关 / 白名单 | `featureFlag`、`whitelist` |

## 新增物种类 → 重点维度

| 新增的是什么 | 重点维度（必须逐项表态） | 通常不受影响 |
|---|---|---|
| **类型 / 类别 / 种类** | ①②③④⑤ **全覆盖** | ⑦（除非要独立权限） |
| **入口 / 按钮** | ①③ | ②④⑤ |
| **字段** | ③④⑥ | ②⑤⑦ |
| **状态 / 流程节点** | ②⑤⑥ | ①③（除非改变展示） |
| **业务规则 / 校验** | ③④ | ①⑤ |
| **角色 / 权限** | ⑦① | ②③④ |
| **渠道 / 来源** | ①②④⑥ | ③⑤ |
| **配置 / 开关** | ⑦③ | ①②④⑤ |

> 「类型」是覆盖面最广的一类 —— 这正是"新增一个类型"容易漏改的原因。

## 扫描结论怎么变成问题

扫描底稿给的是**结论**，不是问卷。每一行的结论只有两个去处（取决于走哪条分支）：

| 结论 | 去处 | 写法 |
|---|---|---|
| **需澄清** | 变成一条**方案遗漏**，进 `问题澄清.md` 的「第二部分 · 方案遗漏」 | 问题 + 现状行为 + 可选解读 + 建议默认 + `file:line` 证据 |
| **无需调整** | 计入 `问题澄清.md`「排查范围」表的「确认不受影响」列 | 存量功能 + 现状行为 + `file:line` + 一句为什么不受影响 |

> **走路径 B（无疑点）时**，上表的落点换成 `实现方案.md` 的「存量功能结论落地对照」表 —— 「需澄清」的此时应为空，全部是「无需调整」或已落地的改动项，**每条都要有落点**（含「沿用现有」的显式声明）。

扫描在**对话内完成**，结论直接落进交付物（问题澄清 / 实现方案），不单独落盘底稿。交付物里只保留两张表：**问题澄清**（方案疑点 + 方案遗漏 + 排查范围声明）和**实现方案**（存量功能结论落地对照）。逐项明细留在每条问题的「给开发」段里。

**产品只面对一份文件。** 问题澄清里既要方案疑点（矩阵给的）也要方案遗漏（扫描给的），按同一套级别排序，共用同一个汇总表。产品不需要在两张表上分别作答。

## 常见漏盘点的地方（交付前对照检查）

- [ ] **产出物落点**：方案说"申请条码/生成回单/出具证书"，但列表/明细/导出里**没有承载该产出物的字段**——模块名带产出物却无处可看，最严重遗漏（维度①反向检查）
- [ ] **操作入口完整性**：列表"操作"列有按钮，但按钮背后的**入参/可选范围/目标页面/批量or单条**没定义（维度②纵向检查）
- [ ] **明细/详情页原型**：列表有"查看明细"入口，但方案没给明细页字段/布局——一条主单对应多条明细（如返回的条码列表）时必漏
- [ ] **导出字段清单**：只说了导出范围（哪些记录），没说导出**哪些字段列**、是否含明细展开
- [ ] **导出**：列表过滤了，导出没过滤（导出常走另一条 SQL / 另一个 service）
- [ ] **统计 / 看板**：按状态 `count` 的，新类型没纳入
- [ ] **待办 / 消息中心**：新类型不进待办列表
- [ ] **对外 API**：类型枚举对外暴露，**第三方需要适配**（这条要单独通知对接方）
- [ ] **定时任务**：按状态扫的任务，新类型会被自动卷进来（有时是想要的，有时是意外）
- [ ] **唯一约束 / 幂等键**：新建的 key 与存量冲突
- [ ] **存量数据解释**：老数据在新增维度下算哪一类？（影响存量列表可见性）
- [ ] **打印 / 导出模板**：新类型的文案不在模板里
- [ ] **审计 / 操作日志查询**：日志界面按类型筛选，新类型查不到
- [ ] **缓存 / 下游同步**：新类型没让下游刷新
- [ ] **数据迁移**：加字段 / 加枚举后，存量行怎么填
- [ ] **兜底分支**：新类型没显式表态，掉进 `default` 抛错

## 与覆盖矩阵的关系

| | 七维度扫描 | 覆盖矩阵 |
|---|---|---|
| 产出 | 方案遗漏 + 无需调整清单 | 方案疑点（`?` / `⚠` / `⚔` 格） |
| 粒度 | 存量功能 × 要不要改 | 事实 × 需求条目 |
| 回答 | 要改 / 不改 / 怎么改 | 覆盖 / 未覆盖 / 矛盾 |
| 作用 | 保证**广度**（不漏维度） | 保证**深度**（不漏细节） |

扫描管"**有没有漏掉一整类功能**"，矩阵管"**这一类里每一条细节准不准**"。两者都要做，缺一不可。
两边的结论最终汇进同一份 `问题澄清.md`。
