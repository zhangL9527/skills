# 输入引导：把三项收齐再开工

Stage -1 的判定与问法细则。SKILL.md 的 Stage -1 是骨架，这里是细节。

## 为什么是这三项

三项任一错 → 整份交付物作废，不是"有点偏差"：

| 项 | 错的后果 |
|---|---|
| 项目地址错 | 代码基线指向另一个项目，所有 `file:line` 证据指向隔壁代码 |
| 方案地址错 | 澄清的是另一份方案，产出的问题单产品看不懂 |
| 取证分支错 | 扫出的是开发中间态，缺陷里一半是伪缺陷 —— 产品分不清真伪，整份文档可信度归零 |

**没有代码库就没有事实基线。** 两端基线各自独立：后端猜错毁后端结论，前端猜错毁前端结论。

## 三项必填输入

| # | 输入 | 组成 | 缺省 | 校验方式 |
|---|---|---|---|---|
| ① | **项目地址** | 后端仓库根 + 前端仓库根（两个独立仓库） | 当前终端目录 | 目录存在 → 是 git 仓库根 → 含源码文件 |
| ② | **方案地址** | 本地路径 或 `http(s)` URL | 无，必填 | 文件存在可读 / URL 能抓到正文 |
| ③ | **取证分支** | 后端分支 + 前端分支 | `master`，该仓无则 `main` | 该分支在对应仓库存在 |

**产物输出目录**是第四项（可派生，默认 `<当前终端目录>/req-clarify-out/`），不用问，只回显。

---

## 判定：问什么，不问什么

### 来源优先级

```
命令行参数  >  本轮对话已说  >  环境扫描（预填，不作默认）  >  问
```

### 硬规则：已经给过的值不再问一遍

重复问已答项是噪音 —— 使用者会以为 skill 没听懂，整轮体验崩掉。

| 情况 | 处理 |
|---|---|
| `--repo-backend` / `--repo-frontend` 已给 | 视为**使用者已确认该路径**，不再问路径 |
| 对话里已说「后端是 xxx 仓」 | 直接采用，回显时标来源「对话」，不再问 |
| 方案地址已给出（参数或对话） | 不问 |
| 分支已指定 | 不问 |
| 前端明确说「本次只看后端」 | 前端记「无」，不追问 |

**只对真正缺失的项提问。** 缺三项时问三项，缺一项时只问一项。

### 问的顺序

```
① 项目地址  →  ③ 取证分支  →  ② 方案地址
```

先定"在哪个代码库、哪个分支上取证"，再收方案 —— 顺序反过来会让使用者在还不知道代码上下文时面对一个空路径问题。

一次 `AskUserQuestion` 最多 4 个问题；缺项超过 4 个时按上面的顺序分批，**每批问完先回显一次**，不要攒到最后一次性问。

## ① 项目地址

### 先扫环境，再问

不要让使用者凭空想路径。跑：

```bash
bash <skill目录>/scripts/scan-repos.sh [当前终端目录]
```

脚本会输出：每个候选仓库的绝对路径、端归属（后端/前端/前后端/未判定）、当前分支、有无 master/main、有无提交、未提交文件数、构建标记，外加一份 TSV。

> **脚本路径**：`<skill目录>` = 本 SKILL.md 所在目录（脚本在它的 `scripts/` 下）。装在项目级是 `<项目>/.claude/skills/req-clarify/`，装在用户级是 `~/.claude/skills/req-clarify/`。**调用前先确认实际位置** —— 脚本不存在时直接手写等价的 `ls`/`git` 探测命令，不要因为路径不对就跳过扫描。

### 端归属怎么判

- **后端**：`pom.xml` / `build.gradle` / `build.gradle.kts` / `settings.gradle` / `go.mod` / `Cargo.toml` / `pyproject.toml` / `*.sln`
- **前端**：`package.json` **且** 依赖里命中 `vue` / `react` / `vite` / `nuxt` / `next` / `svelte` / `@angular/core` / `uni-app` / `taro` / `webpack`
- **只有 `package.json` 没有前端框架依赖** → **不算前端仓**。多仓工作区根常放一个空壳 `package.json` 当骨架，把它当成前端仓会扫出一堆假事实。
- 两者都有 → 前后端同仓

### options 怎么构造

1. **label 写绝对路径** —— 使用者要拿去填参数，绝对路径才是能直接粘贴的值。只写仓库名，使用者还得自己拼路径。
2. **description 附关键信息**：当前分支、有无 master/main、是否空仓库/无提交。让人一眼看出哪个候选是安全的基线。
3. **候选多于 3 个时只列 3 个最可能的**，其余靠「其他」填。挑选顺序：
   - ① 当前工作区分支是 feature 的（说明正在开发，最可能是本次范围）
   - ② 仓库名 / 模块名与方案改动范围吻合的
   - ③ 其余按仓库名字母序取首个
4. **「其他」永远保留** —— 使用者填自定义路径的唯一入口，不要省。
5. 前端选项里保留一条 **「无（本次仅后端）」**。前端标记为「无」时跳过前端基线，交付物头部前端一行写 `前端：无（本次仅后端）`。

### 多仓场景怎么取值

一个项目拆成多个后端仓（如 `xxx-logistics-center` / `xxx-wms` / `xxx-stock-center`）时：

- **「后端代码库路径」填本次改动的后端主责仓** —— 按方案涉及的模块归属判断
- 其余涉及仓在 Stage 1 作为**补充事实来源**单独读取（不必跑 `prepare-baseline.sh`，但要记住它的分支与提交）
- 交付物头部**仍只写两行**（后端主责仓 + 前端），补充仓写在「排查范围」里

选主责仓时若方案跨多个后端仓，**问清楚**：在 options 的 description 里标明"本次范围可能涉及 N 个后端仓"。

## ③ 取证分支

### 默认值逐端算

```
后端默认 = master，该仓无 master 则 main
前端默认 = master，该仓无 master 则 main
```

**两端分别算** —— 前端仓常见只有 `main`，后端只有 `master`。写死 `master` 会让前端那端直接落到降级情形。

### options

1. `确认：后端 <分支> / 前端 <分支>`
   描述：「干净的主干基线，不受工作区当前分支影响，结论最可信。★推荐」
2. `当前工作区分支`
   描述：「后端 <WT分支> / 前端 <WT分支>；工作区可能是开发中间态（新代码没提交、老代码已改过、有半成品重构），扫出的现状会失真 —— 仅在本次要澄清的正是该分支上的需求时选」
3. 其他 → `后端:xxx 前端:yyy` 格式

### 必须说明的风险，但不能替使用者决定

选 2 是**合理**的：本次需求若正是某个 feature 分支上的开发，当前分支才是真实上下文，master 上扫到的"现状"反而是过时的。

但必须让使用者知道两件事：

- 工作区的**未提交改动不会进入基线**（`git archive` 只导出分支上的已提交内容）
- 结论里的"现状"是**分支提交态**，不是他本地工作区此刻的样子

**不要只推 master 就完事**，也不要因"工作区不干净"就替他否决当前分支 —— 决定权在使用者。

## ② 方案地址

### options

1. **候选方案文档** —— 扫描当前目录及其一层子目录里的 `md` / `txt` / `doc` / `docx` / `pdf`，文件名含 方案 / 需求 / PRD / plan / spec / 设计 等关键词，最多 3 个。label 写相对路径 + 大小。
2. `扫一遍当前目录的文档，逐个列标题让我选` —— 使用者不确定是哪份时的兜底。
3. 其他 → 本地绝对路径 或 `http(s)` URL。

**需登录的链接必须先下载再填本地路径** —— `WebFetch` 抓不到受保护页面的正文，抓到的往往是登录页，澄清的却是登录页。

---

## 校验：不合格怎么办

每一项都要实测。**不合格时只重问那一项**，并说清「哪一项不合格 + 实测结果」：

| 情形 | 话术 | 处理 |
|---|---|---|
| 路径不存在 | 「路径 `<p>` 不存在」 | 重问该项 |
| 不是 git 仓库 | 「`<p>` 不是 git 仓库（`git rev-parse` 失败）」 | 重问该项 |
| 是空目录 / 无源码 | 「`<p>` 下没找到源码文件」 | 重问该项 |
| 方案文件读不到 | 「`<p>` 打不开」/「`<url>` 抓不到正文（可能需登录）」 | 重问该项，或请其先下载 |
| 分支不存在 | 「`<repo>` 没有分支 `<b>`，现有分支：…」 | 重问该项 |

**不许将就。** 路径错就重来，不要对着空目录编出一份"完整"的问题单 —— 那比不做更糟：它看起来很完整，但每条证据都是假的。

## 回显：六项一次说完

三项收齐后，一次性回显一张表请使用者核对：

| 项 | 值 | 来源 |
|---|---|---|
| 方案地址/路径 | … | 参数 / 对话 / 本轮确认 |
| 后端代码库路径 | … | 同上 |
| 前端代码库路径 | … | 同上 |
| 后端取证分支 | … | 同上 |
| 前端取证分支 | … | 同上 |
| 产物输出目录 | … | 默认 |

**回显后才进入 Stage 0。**

### 产物目录的落点

默认 `<当前终端目录>/req-clarify-out/`。

当前终端目录**不是工作区根**时（它本身是某个仓库的子目录，或它就是那个多仓工作区的根但下面并列着多个仓库），提示一句即可、**不阻塞**：

> 「当前终端目录 `<pwd>` 看着是 `<repo>` 的子目录 / 工作区根，产物建议落到 `<root>/req-clarify-out/`」

---

## 草稿文件：默认不写

v3.2.0 起，交付物目录只放 3 个交付物，过程不落盘。**输入表单默认只渲染在对话里。**

使用者明确要文件时（说「给我个文件填」/「我填完告诉你」），才写 `<当前终端目录>/req-clarify-input.md`，并在最后说明它是**临时草稿、可删、不归档进交付物夹**。

---

## 速查：一次问全时的样子

```
Q1 后端代码库  ─ 绝对路径 + 当前分支/有无 master（≤3 个候选 + 其他）
Q2 前端代码库  ─ 绝对路径 + 当前分支/有无 master（≤3 个候选 + 无 + 其他）
Q3 取证分支    ─ 确认 master/main ｜ 当前工作区分支 ｜ 其他（后端:xxx 前端:yyy）
Q4 方案地址    ─ 候选文档 ｜ 逐个列标题 ｜ 其他（路径/URL）
```

**先确认路径再问分支** —— 分支选项的文案依赖具体仓库路径（默认 `master` 还是 `main`、当前分支叫什么），路径没定就问分支会给出错误的默认值。
