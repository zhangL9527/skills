# 需求澄清：方案 × 代码库 → 澄清问题单 / 具体实现方案

## 定位

**这是一个需求澄清工具，只产出 Markdown 文档，不产出任何代码。**

输入：一份产品方案 + 一个代码库。
输出（**取决于方案有没有问题**）：

| 方案状态 | 产出 | 交给谁 | 下一步 |
|---|---|---|---|
| **有疑点** | **澄清问题单** —— 所有不完整、有疑问、缺失的地方，逐条带代码证据 | 产品 | 产品**改方案** → 提交新方案 → 重跑 |
| **无疑点** | **具体实现方案** —— 变更点、类名方法、表结构、验收标准俱全 | 开发 / AI 编码代理 | 直接编码 |

**方案没问题就不出澄清问题单。** 硬造一份问题单是噪音 —— 产品分不清哪些是真缺陷、哪些是凑数，反而降低了整份文档的可信度。

只有两个目的：**把方案澄清到无歧义**，以及**把实现依据写到位**。

不负责：写代码、给产品代做决策。

> **产品与澄清工具之间的交互只有一种：改方案。** 没有"填答复表"、没有"裁决"环节 —— 问题单是**只读交付物**。

## 输入（四项，缺一不可）

| 参数 | 必填 | 说明 |
|---|---|---|
| 方案文档地址或路径 | ✅ | 产品的方案原文。本地文件（md / doc / docx / txt / pdf 文本均可），或可公开访问的 `http(s)` URL |
| 代码库路径 | ✅ | 要对照的代码库根目录。**默认取当前终端目录，但必须经使用者确认才生效** |
| 产物输出目录 | — | 默认 `<当前终端目录>/req-clarify-out/` |
| 代码分支 | — | **默认 `master`，无则 `main`**；可显式指定其它分支。**只在哪个分支上取证** —— 见下方「代码基线」 |

**没有代码库就没有事实基线** —— 遗漏是相对于代码里真实存在的东西而言的，代码库猜错，整份问题单的可信度归零。

**缺参数时的处理**：**不要自行假定，走 Stage -1 输入表单**（见下）—— 出**一份文档形式的表单**让使用者填，而不是口头追问两句。

**校验 repo**：路径存在、可读、里面确实有代码（能找到源码文件）。是空目录 / 不是代码库 → 问用户确认，不要对着空目录编出一份"完整"的问题单。

## 代码基线：只在 master / main 上取证

> **开发常常忘记切分支。** 工作区停在 feature 分支上时，扫出来的"现状"其实是**开发中间态** —— 新写的代码没提交、老代码已被改过、还有半成品重构。这时候澄清出来的"缺陷"有一半是伪缺陷：产品看到的是他自己刚改到一半的东西。

**规则：所有代码事实一律来自 `master` 或 `main`，与工作区当前在哪个分支无关。**

**做法：导出一份只读副本，全程在副本上作业** —— 不切使用者的工作区，不碰他的未提交改动，也不要求他记得切分支。

```bash
bash ~/.claude/skills/req-clarify/scripts/prepare-baseline.sh <代码库路径> <产物目录>/.baseline
```

脚本自己判断三种情形，**不猜**：

| 情形 | 判定 | 基线 | 必须告知使用者 |
|---|---|---|---|
| **A** | 有 master/main，且其内容完整覆盖工作区源文件 | 该分支的导出副本 | 否 |
| **B** | 有 master/main，但有源文件**未被 git 跟踪** | 分支副本 + 补入工作区未跟踪源文件 | **是** —— 该分支不是完整基线 |
| **C** | 无 master/main（无提交 / 非 git 仓库） | 直接用工作区 | **是** —— 证据取自工作区，工作区不对结论就失真 |

**情形 B 常见于"源码没纳入 git 管理"的仓库** —— 例如只提交了后端 `.java`、前端 `.vue`/`.js` 全是未跟踪状态。这种情况下 `git archive` 会把整个前端悄悄丢掉，必须补回来并明确标注。

**分支与提交必须记进所有产物的头部**：`代码库：<路径>@<分支>@<提交>`；情形 C 写成 `代码库：<路径>@<工作区现状（无 master/main）>`。

**后续所有读取（survey / Read / Grep / verify-citations）都指向基线目录，不指向工作区。**

## 核心模型：差集即缺陷

> 方案 = 意图（不完备、内部可能自相矛盾）
> 代码 = 现状事实（完备、可验证、可追溯）

**澄清不是"读懂方案"，是求差集：**

```
缺陷集 = 代码事实空间 − 方案意图空间
```

四类痛点都是差集的不同表现，**一个机制（覆盖矩阵）覆盖全部四类**：

| 痛点 | 差集形式 | 矩阵表现 | 检查器 |
|---|---|---|---|
| 功能描述遗漏 | 事实存在，方案无条目命中 | **空格** | C1 覆盖 |
| 前后相互矛盾 | 两条意图对同一事实给出互斥值 | **冲突格** | C2 一致 |
| 描述过于简洁 | 条目命中对象但属性未给全 | **半填格** | C3 完备 |
| 流程节点遗漏 | 现状节点无对应方案条目 | **流程空格** | C4 流程等价 |

## 第二条主线：广度

**新增一个类型 / 入口 / 字段 / 状态 / 规则，不是"加一个东西"，而是给系统加了一个新的分流维度。**

> 凡是**对这个维度分流**、或**受这个维度影响**的存量功能，都必须表态：新东西来了，它要不要跟着变？

产品最常犯的错不是"改错了"，而是**"没想到要改"**。方案只写新东西怎么实现，存量功能一个字不提 —— 五个按钮共用一个查询入口、导出走另一条 SQL、统计按状态 count、定时任务按状态扫、对外 API 暴露了类型枚举…… 每一条都会漏。

**这一类问题不能靠"问几个问题"解决，要靠一次系统性的扫描。** 七个维度逐个扫，扫完的结论全部落进交付物（有问题 → 澄清问题单；无疑点 → 实现方案的「存量功能结论落地对照」）：

```
覆盖矩阵  → 管「深度」：这一类里每一条细节准不准
七维度扫描 → 管「广度」：有没有漏掉一整类功能
```

**两条线问的不是同一件事，所以都要做 —— 但它们不是两类问题，是两种问法：**

| | 问的问题 | 结论是什么 |
|---|---|---|
| 覆盖矩阵 | 方案**有没有提到**这个事实 | 提到但没说全 / 矛盾 → **方案疑点** |
| 七维度扫描 | 这个存量功能**会不会被波及** | 波及但方案没提 → **方案遗漏**；不受影响 → 计入排查范围声明 |

**七维度扫描是产出「方案遗漏」的方法，不是第三类问题。** 交付物里只有「方案疑点 + 方案遗漏」两类 —— 扫描底稿是**工作稿**，它的逐项明细不占交付物的篇幅，只把结论汇总成问题单里的「排查范围」表。

它独有的两样东西：① **完整性 checklist** —— 七个维度是"扫全了"的闭集定义（尤其覆盖事实抽取容易漏掉的展示类入口、权限配置类点位）；② **「无需调整」免责结论** —— 覆盖矩阵只记录对不上的地方，没有地方记录"查过了、不受影响"。

扫描维度、代码枚举方法、常见漏盘点的地方，见 `references/impact-inventory.md`。

## 为什么必须读代码

纯读方案永远只能发现"方案自相矛盾"，发现不了"方案没提的"。因为**遗漏是相对于代码里真实存在的东西而言的**。

代码事实至少有六类（不是"业务流程 vs 功能描述"两类，分类要更细才能定位）：

1. **入口事实** — 页面/接口上所有操作入口及其背后动作（按钮、菜单、API）
2. **类型事实** — 业务类型枚举的**全部取值**，以及每个取值触发的差异化分支
3. **字段事实** — 涉及对象的**完整字段集**，及每个字段的**所有写入路径**
4. **流程事实** — 状态集合 + 状态流转边 + 每条边的守卫条件与副作用
5. **约束事实** — 校验规则、默认值、权限点
6. **副作用事实** — 发消息、写日志、建任务、调第三方、对账等

> **新增一个类型 → 最危险的是类型事实中的"差异化分支"**。代码里凡有 `switch(type)` / `if (type == X)` 的地方，新增类型都要落到某个分支上。方案通常只说新类型自己的分支，漏掉"老分支要不要排除新类型"。

抽取方法与检索模式见 `references/fact-extraction.md`。

## 执行流程（输入表单 + 六阶段 + 一个分支点）

每个阶段的**产物**和**放行门**都必须落盘，不允许跳阶段口头带过。
**Stage 5 是分支点** —— 方案有没有问题，决定后面产出澄清问题单还是具体实现方案。

### Stage -1 · 输入表单（未填不得进入 Stage 0）

**无参数运行 `/req-clarify` 时先走这一步。** 输入不是"问两句"就完事，是**出一份文档形式的表单**让使用者填 —— 填完一次到位，后面不再追问同样的问题。

1. **取当前终端目录**：`pwd`。
2. **渲染表单**：以 `templates/input-form.md` 为模板生成一份**已预填**的表单，写入 `<当前终端目录>/req-clarify-input.md`：
   - 「代码库路径」预填 `<当前终端目录>`，标 **默认 · 待确认**
   - 「代码分支」预填 `master`（该库没有 master 则填 `main`），标 **默认 · 待确认**
   - 「产物输出目录」预填 `<当前终端目录>/req-clarify-out/`
   - 「方案文档地址或路径」留空，标 **必填**
3. **在对话里把表单原样贴出来** —— 使用者不打开文件也能直接填。
4. **确认代码库路径**（必须显式确认，见下）。
5. **收方案文档地址或路径**：使用者在对话里回复即可；也可让使用者编辑 `<当前终端目录>/req-clarify-input.md` 后回复「已填写」，此时读该文件取值。
6. **回显最终四项**（方案地址/路径、代码库路径、代码分支、产物目录）供使用者核对，确认后把结果归档为 `<out>/输入表单.md`（本次运行的输入存根），并说明 `<当前终端目录>/req-clarify-input.md` 是临时草稿、可删。

**确认代码库路径（`AskUserQuestion`）**

默认是当前终端目录，但**默认 ≠ 生效** —— 必须让使用者点头：

- header `代码库路径`；question：`代码库路径确认：默认使用当前终端目录 <当前终端目录>。确认吗？（要用别的路径，选「其他」并填写完整路径）`
- options（2–4 条，顺序固定）：
  1. `确认：<当前终端目录>` —— 描述「作为代码库根路径，所有 `file:line` 证据相对它」
  2. `上级目录：<父目录>` —— 描述「当前目录可能只是仓库的子目录时选它」
  3. 子目录候选 —— 扫描 `<当前终端目录>` 一层子目录里带 `.git` / `package.json` / `pyproject.toml` / `go.mod` / `pom.xml` / `Cargo.toml` / `build.gradle` / `*.sln` 的目录，最多 2 个，各标「疑似代码库」

**确认代码分支（`AskUserQuestion`）**

默认 `master`（无则 `main`）。**默认 ≠ 生效**，但这一项的确认可以和路径确认合并成一次提问：

- header `代码分支`；question：`代码分支确认：默认只读 <分支>（master / main）。确认吗？换分支取证请选「其他」填写完整分支名。`
- options：
  1. `确认：<分支>` —— 描述「只在这个分支上取证，不受工作区当前分支影响」
  2. `当前工作区分支 <WT_BRANCH>` —— 描述「**不推荐** —— 工作区可能是开发中间态，扫出来的现状会失真；仅在你确实要以它为基线时选」

**收方案文档地址或路径（`AskUserQuestion`，仅当使用者未在对话里给出时）**

- header `方案文档`；question：`方案文档地址或路径？本地文件或可公开访问的 URL；需登录的链接请先下载再填本地路径。可选「其他」直接填写完整路径。`
- options（2–4 条）：
  1. 候选方案文档 —— `<当前终端目录>` 及其一层子目录里扫描到的 `md` / `txt` / `doc` / `docx` / `pdf`，文件名含 方案 / 需求 / PRD / plan / spec 等，最多 3 个，各标相对路径与大小
  2. `扫一遍当前目录的 md，逐个列标题让我选` —— 描述「我不确定是哪份时选它」
  3. 候选与第 2 条合计不足 2 条时，补 `方案文档还没准备好（本次不开始）`

**带参数运行时的处理**：`/req-clarify <方案地址或路径> --repo <代码库路径> [--out <目录>]` —— 跳过提问，把参数直接作为表单初值（`--repo` 给出的路径视为**使用者已确认**），其余流程完全一致。

### Stage 0 · 输入解析 + 基线锁定
1. 校验输入：方案文档可读（本地路径 → `Read`；`http(s)` URL → `WebFetch` 抓正文，抓不到或需登录 → 回头问使用者要本地文件）、代码库路径有效（见上方「输入」）。
2. **锁定代码基线**（见上方「代码基线」）：

```bash
bash ~/.claude/skills/req-clarify/scripts/prepare-baseline.sh <代码库路径> <产物目录>/.baseline [--branch <分支>]
```

   读它的报告，确认三件事：**基线分支 + 提交号**、**基线目录**、**是否有降级情形**。
   - 情形 B / C → **必须把降级事实告诉使用者**（"该分支不是完整基线" / "证据取自工作区现状"），并请他确认工作区就是主干代码。
   - 情形 A → 直接往下走，不必打扰使用者。
   - **从这一刻起，所有代码读取都指向基线目录，不指向工作区。**
3. 读方案文档，拆成**可编号的需求条目** `REQ-001...`，每条标注：改动对象、目标、是否含字段级描述。
4. 判断方案是否可解析（见 G0）。方案过于零散时，先按"对象"重组成条目。
5. 明确本次改动**作用域**：哪些模块/页面/接口在范围内。作用域之外的代码事实**不作为缺陷上报**（见下方红线）。
6. **识别本次新增物的种类**（类型 / 入口 / 字段 / 状态 / 规则 / 角色 / 渠道 / 配置）—— 决定 Stage 2 的重点维度。

**产物**：`00-方案解析.md`（条目清单 + 新增物种类 + **基线分支与提交**）

### Stage 1 · 代码事实抽取
按六类事实逐一抽取，**要全集，不要抽样**。每条事实带 `file:line` 证据。

**所有读取都基于 Stage 0 锁定的基线目录** —— 不是工作区。

建议先跑 `scripts/survey.sh` 做机械线索定位（脚本只定位，判定由你做）：

```bash
bash ~/.claude/skills/req-clarify/scripts/survey.sh <基线目录>
```

**产物**：`01-代码事实基线.md`（模板 `templates/fact-baseline.md`，头部记基线分支与提交）

### Stage 2 · 七维度扫描（管广度）
把 Stage 1 的事实按**七个维度**归类，逐条问"新增的这批数据，要不要影响它"：

| 维度 | 问什么 |
|---|---|
| ① 数据可见性 | 在哪些地方出现 / 不出现（列表、**导出**、统计、待办、消息、对外查询）；**反向必做**：方案声明的产出物/返回值（条码、回单号、外部回写号）在列表/明细/导出有没有字段落点 |
| ② 行为分流 | 走哪条分支（switch/策略/状态机/**兜底分支**）；**纵向必做**：每个操作入口/按钮背后的可选范围、批量/单条、入参（前端传什么/后端补什么）、目标页面是否定义 |
| ③ 字段与校验 | 字段怎么填、校验要不要变（默认值、非空、唯一、上限） |
| ④ 副作用 | 会不会触发（MQ、消息、日志、任务、**额度/积分/库存**、第三方、对账） |
| ⑤ 流程与时效 | 走哪条流程、时限变不变（超时、自动流转、驳回清理） |
| ⑥ 对外与集成 | 对外暴露成什么样、**下游要不要适配** |
| ⑦ 权限与配置 | 要不要单独的权限 / 开关 / 白名单 |

每个维度扫完，结论只有两种去处：

- **有疑点** → 写成一条**方案遗漏**（见下方问题单结构）
- **确定不受影响** → 计入问题单「排查范围」表的「确认不受影响」列，**底稿里带一句理由**

> **走路径 B（无疑点）时**，落点换成 `05-具体实现方案.md` 的「存量功能结论落地对照」表 —— 此时「需澄清」应为空，全部是已落地的改动项或「沿用现有」的显式声明。

扫描底稿用 `templates/impact-inventory.md` 记录。

**产物**：`02b-七维度扫描底稿.md` —— **工作稿，不发给产品**，但**必须落盘**：
它是问题单「排查范围」表的证据底座（G1b 要求每条「需调整」和「无需调整」都带 `file:line`），也是每轮重扫时与上一轮对比「结论变迁」的依据。

**规则**：
- 同一根因合并成**一项**（5 个按钮共用一个查询 = 1 条疑点，不是 5 条）
- **「不受影响」也要显式写出来** —— 它是免责证据，也是让产品知道"这里查过了"的凭据
- 每条都必须带 `file:line`，没证据的不写

### Stage 3 · 覆盖矩阵构建（管深度）
行 = 代码事实，列 = 需求条目。

**每个格子必须填三态之一**，空格不允许存在：
- `✔` 方案已覆盖且无歧义
- `✘` 方案明确说不涉及（也算覆盖，带理由）
- `?` 方案未提及 → **缺陷候选**

**产物**：`02-覆盖矩阵.md`（模板 `templates/coverage-matrix.md`）

### Stage 4 · 检查器 + 疑点定级
对矩阵跑 C1–C4 检查器（规则见 `references/checkers.md`），每个 `?` 格转成一条**方案疑点**；再把 Stage 2 的方案遗漏并进来。

**产物**：疑点清单（工作稿，落进 `02-覆盖矩阵.md` 与扫描底稿即可）—— **这一步先不出交付物**。

### Stage 5 · 放行判定 ★分支点

**判定规则**：疑点清单**非空** → 路径 A；**为空** → 路径 B。

#### 路径 A · 有疑点 → 产出澄清问题单

1. 按 `templates/issue-list.md` 产出 `03-澄清问题单.md`（双层结构 + 排查范围表）
2. **证据自检（必做）**：

```bash
bash ~/.claude/skills/req-clarify/scripts/verify-citations.sh <基线目录> 03-澄清问题单.md 01-代码事实基线.md 02-覆盖矩阵.md 02b-七维度扫描底稿.md
```

   它会输出每一处引用指向的那一行内容 —— **逐行核对语义是否对得上**。
   行号有效但指向相邻字段的情况，校验器查不出来，只能靠人眼看预览。

3. 在 `04-迭代纪要.md`（模板 `templates/iteration-log.md`）追加本轮记录：提了什么、产品改稿要点、还剩什么
4. **流程到此暂停并交付** —— 产品**只读**这份问题单，改完方案提交回来

**重跑（产品提交新方案后）**：Stage 0 ~ Stage 4 全部重跑 —— 产物覆盖，纪要**追加**轮次。
一次改稿常常连带影响别处：新类型的定义变了，七个维度要重扫，矩阵里所有格子也要重看。

**循环直到疑点清单为空。** 高/中级疑点必须清零；低级别疑点允许带默认建议进入路径 B，但要在实现方案的「不做清单」或「边界与异常」里写明。

#### 路径 B · 无疑点 → 直接产出具体实现方案

**不出澄清问题单。** 方案没问题，问题单里全是"无需调整"，对产品毫无价值。

进入 Stage 6。

### Stage 6 · 具体实现方案
按 `templates/implementation-plan.md` 产出 `05-具体实现方案.md` —— 一份**AI 可参照直接完成编码**的实现依据。

**必须写到位**：改哪个文件、改哪一处、改成什么（变更点行号 + 锚点方法名）、类名方法、表结构 DDL、枚举取值、接口契约、流程与失败处理、逐条验收标准。

**仍不产出代码** —— 给的是改动指令与关键片段，不是完整实现类。

**追溯附录必须含「存量功能结论落地对照」**：每一条方案遗漏、以及每一条「无需调整」，都要在实现方案里有落点。**「不受影响」也要写出来**（写明"沿用现有"）—— 否则无法验证每个结论都落地了。

**产物**：`05-具体实现方案.md`

## 澄清问题单：双层结构

这是**路径 A 下的主交付物**。一份文件同时给产品和开发看：上层给产品，下层给开发。

```
### Q-007 [高] 新类型在「待审核」列表中是否可见

**给产品（一句话）**
新类型订单要不要出现在原有五个按钮的列表里？

**给开发**
- 证据：`src/service/orderService.ts:88`（五个按钮共用同一查询入口 queryOrders）
- 现状：五个按钮的过滤条件只按 status 区分，未按 type 区分；新增 type=T 后会出现在全部五个列表
- 可能解读：
  1. 老列表一律排除 type=T（需在共用入口加过滤，影响五个按钮）
  2. 老列表保留 type=T（无需改动）
- 建议默认：解读 1 —— 因为老列表的操作按钮对 T 不适用
```

****没有代码证据的问题不要提** —— 产品会答不准，答不准就等于没澄清。

**问题单是只读的**：没有"答复记录"表、没有"已裁决"状态。产品读完直接**改方案**，改完提交回来重跑。

问题单分两部分，**标题用产品看得懂的说法**：

- **第一部分 · 方案疑点** —— 来自覆盖矩阵（方案条目 × 代码事实）。方案**已经写了**的那条要求，本身没说全、前后矛盾、或与代码对不上。
- **第二部分 · 方案遗漏** —— 来自七维度扫描（存量功能 × 新增物分流维度）。方案**完全没提**、但会被本次新增物波及的存量功能。

两者共用同一套结构、按同一套级别排序，产品只看一份清单。

> 内部术语仍叫「深度」（覆盖矩阵管深度）与「广度」（七维度扫描管广度）；**面向产品的产物里一律用「方案疑点 / 方案遗漏」**，不要把「深度 / 广度」暴露给产品。
> 汇总表的「来源」列取值随之写成 `方案疑点` / `方案遗漏`；维度标注列统一叫「**影响维度**」（深度来源的问题同样带维度标注）。

详见 `templates/issue-list.md`。

## 质量门（逐阶段卡口）

| 门 | 阶段 | 放行条件 |
|---|---|---|
| **G0** 输入可解析 | 0 | 输入表单已填写并回显确认；方案条目已编号；每条有改动对象；作用域已圈定；新增物种类已识别；**代码库路径已确认有效**；**基线分支已锁定（master/main 或使用者显式指定），基线目录已生成，降级情形已如实告知** |
| **G1** 事实完备 | 1 | 六类事实均已抽取；每类有"全集"声明（枚举全、字段全、节点全） |
| **G2** 覆盖无空洞 | 3 | 矩阵**零空格**；每个 `?` 都有对应疑点 |
| **G3** 矛盾清零 | 4 | 方案内部无自相矛盾；与代码事实的矛盾已在方案里被修正，无悬空冲突 |
| **G4** 属性完备 | 4 | 无半填格：要么补全赋值，要么标注"不修改" |
| **G5** 流程等价 | 4 | 现状节点与方案节点一一映射；差异节点在方案中已说明 |
| **G1b** 扫描无盲区 | 4 | 七个维度均已扫过；每条方案遗漏与每条"无需调整"都带 `file:line` |
| **G6** 文档自洽 | 6 | 实现方案零未决项、零内部矛盾、零隐含假设；**存量功能结论每条有落点** |
| **G7** 可编码性 | 6 | 每个改动项都有 `file:line` + 锚点方法名 + 可照抄的改法；枚举变更列全所有同名位置；流程每步有失败处理；验收标准逐条可执行；零 `TBD`/`待确认` |

细则见 `references/gates.md`。**任何一门未放行，不得进入下一阶段** —— 带着未澄清项进 Stage 6，等于把歧义直接喂给编码代理：它不会提问，会选一个"最合理的默认值"继续写。

## 具体实现方案写作规范

实现方案的第一读者是**AI 编码代理**。它只有一个要求：

> **AI 照着它写代码，不需要再问任何问题。**

AI 遇到空白不会停下，它会继续编。所以**含糊的代价在下游兑现** —— 方案里省下的一句话，会变成下游的一次猜测。

细则见 `references/implementation-writing.md`，硬性要求：

1. **每个改动项定位到「文件 + `file:line` + 锚点方法名」** —— 只给行号，改动后行号漂移，会改到隔壁方法
2. **每个改动项给出可照抄的改法** —— 代码片段或明确步骤，不是"加个判断"
3. **枚举变更列全所有同名位置** —— 后端 `ReturnConst` 与 `Const`、前端 `ENUM.js` 多处，改一处漏一处就有的页面看不到
4. **表结构给 DDL**；字段用表格列全（类型 / 取值 / 何时写 / 为空时行为），并说明"未列出的字段"
5. **接口契约列全入参出参**，无"同上"
6. **流程用步骤表，每步都有失败处理**；定时任务给间隔 / 逻辑 / 完结条件 / 失败策略
7. **必须有「不做清单」** —— 不写，AI 会顺手把方案里"待沟通""后续迭代"的接口也实现了
8. **必须有术语表** —— 同一概念多个名字会造出两套实现
9. **逐条验收标准** —— 写清「操作」和「预期」，覆盖异常路径
10. **存量功能结论落地对照** —— 每条都有落点，「无需调整」写明"沿用现有"

> **仍然不产出代码。** 给的是改动指令与关键片段，不是完整实现类。

## 红线

- **代码库路径必须由使用者确认。** 默认值是当前终端目录，但**未经确认不生效**，也不能静默沿用。确认时把最终路径回显一遍。猜错了整份问题单都不可信。
- **只从 master / main 取证。** 开发常忘记切分支，工作区停在 feature 上时，扫出的"现状"是开发中间态，澄清出的缺陷有一半是伪缺陷。**所有代码读取都指向 Stage 0 锁定的基线目录，不指向工作区。** 基线分支与提交必须写进每份产物的头部。降级到工作区时（无 master/main），**必须在产物里写明「证据取自工作区现状」**，不能让读者以为那是主干代码。
- **作用域外的代码事实不上报。** 一个老模块的字段缺口和产品本次需求无关，混进去会毁掉问题单的可信度。判定规则见 `references/checkers.md`。
- **不替产品做决策。** 只列可选解读 + 标注建议默认值，最终由产品**改方案**来定。决策权归属错了，澄清就变成了"开发替产品写需求"。
- **问题单里不给技术方案。** 问题单讲"业务上这里该是什么"，不讲"建议这么改代码"。除非该技术选择直接影响业务语义（如过滤时机影响数据正确性）。
- **不把"方案写得不够细"直接上报为问题。** 先在代码里找到对应的具体事实锚点，找不到锚点的说明是表达问题，合并到术语表/规范里解决，不要占用产品澄清额度。
- **一个问题的澄清额度有限。** 问题单超过 ~25 条，产品不会逐条改方案。合并同类项、只留真正影响实现的。
- **广度要全量扫，不要只挑"我怀疑有问题的"。** 只给几个猜测性问题，产品会觉得你在找茬；把七个维度扫完、连"确定不受影响"的都列出来，产品才知道"我漏了什么"。**广度靠扫描保证，深度靠追问保证。**
- **不要用"新增的东西怎么实现"替代"存量功能要不要跟着改"。** 前者方案里通常已经写了，后者才是方案里没有的。
- **问题单是只读的，不设"产品答复"环节。** 产品通过**改方案**回应，不在文档里填答复表。**没有答复表** —— 有它就会诱导产品逐条填，而填出来的答案没有落到方案里，等于没澄清。
- **方案无疑点就不出澄清问题单。** 硬造的问题单是噪音：产品分不清哪些是真缺陷、哪些是凑数，整份文档的可信度会被拉低。
- **实现方案必须具体到 AI 不用再问，但不产出完整代码。** 变更点、类名方法、表结构、验收标准要写全；完整实现类不写 —— 那还是代码。
- **不产出代码。** 本 skill 的终点是 Markdown 文档。

## 运行方式

```
/req-clarify                                              # 无参数 → 走 Stage -1 输入表单
/req-clarify <方案地址或路径> --repo <代码库路径> [--branch <分支>] [--out <产物目录>]
```

**无参数运行是默认路径**：先出**输入表单文档**（方案文档地址或路径、代码库路径、代码分支、产物目录），使用者填写 / 确认后才开始。代码库路径**默认当前终端目录**，但要使用者点头才生效；代码分支**默认 master（无则 main）**，同样要确认。

带参数运行则跳过表单提问，参数直接作为表单初值（`--repo` 视为已确认），其余流程一致。
`--out` 省略时，产物默认写到当前目录下的 `req-clarify-out/`。

## 产物清单

```
<out>/
├── .baseline/              # 代码基线副本（master/main 的只读导出）← 工作稿，可删
├── 输入表单.md            # 使用者填写的输入存根（方案地址/路径、代码库路径、分支、产物目录）
├── 00-方案解析.md        # 需求条目编号 + 新增物种类 + 基线分支/提交
├── 01-代码事实基线.md    # 六类事实 + file:line 证据
├── 02-覆盖矩阵.md        # 需求 × 事实，无空格            ← 保证深度
├── 02b-七维度扫描底稿.md  # 逐项排查记录 + file:line       ← 工作稿，保证广度
├── 03-澄清问题单.md      # 方案疑点 + 方案遗漏 + 排查范围    ← ★仅当有疑点
├── 04-迭代纪要.md        # 每轮提出/改掉/剩余，防反复
└── 05-具体实现方案.md    # 变更点+类名方法+DDL+验收标准    ← ★仅当无疑点
```

全部是 Markdown（`.baseline/` 是代码副本）。

**产品只读 `03`（或 `05`）。** `00` / `01` / `02` / `02b` / `04` 是工作稿 —— 给开发和追溯看，不发给产品。

**`03` 与 `05` 二选一，不会同时存在。**

| 情形 | 交付什么 | 接下来谁做什么 |
|---|---|---|
| 方案**有**疑点 | `03-澄清问题单.md`（+ `04-迭代纪要.md`） | 产品**只读**问题单 → 改方案 → 提交回来重跑 |
| 方案**无**疑点 | `05-具体实现方案.md`（+ `04-迭代纪要.md`） | AI / 开发**照着直接编码**，不再提问 |

**`03-澄清问题单.md` 转给产品** —— 它必须自包含：产品不看其它文件也能读懂每个问题、看到证据、据此改方案。
**`05-具体实现方案.md` 转给编码代理** —— 它必须具体到不用再问任何问题（见「具体实现方案写作规范」）。
