# 需求澄清：方案 × 代码库 → 问题清单 / 实现方案

**只产出 Markdown，不产出代码。** 输入：产品方案 + 代码库。输出取决于方案有没有问题：

| 方案状态 | 产出 | 交给谁 | 接下来 |
|---|---|---|---|
| **有疑点** | **问题清单.md** —— 每条带 `file:line` 证据 | 产品 | 产品**改方案** → 提交新方案 → 复用同一夹重跑 |
| **无疑点** | **实现方案.md** —— 变更点/类名方法/DDL/验收标准俱全 | 开发 / AI 编码代理 | 直接编码 |

**方案没问题就不出问题清单**（硬造的是噪音）；**问题清单是只读交付物**（无答复表、无裁决环节 —— 产品只通过改方案回应）。

> 细则按需查：`input-collect.md`（输入引导）· `fact-extraction.md`（事实抽取）· `impact-inventory.md`（七维度）· `checkers.md`（矩阵与检查器）· `issue-worth.md`（提问价值）· `gates.md`（放行门）· `implementation-writing.md`（实现方案写法）

## 产物目录（只有 3 个交付物）

```
<产物目录>/<方案名> 迭代/          # 单夹，每轮覆盖，不分轮次编号
├── 产品方案/                       # 方案原文/原型/截图，保留原始文件名，不转化不重命名
├── 问题清单.md                      # ★仅当有疑点
└── 实现方案.md                      # ★仅当无疑点
```

- **两份交付物二选一**：有疑点 → 只出清单；无疑点 → 只出实现方案，并**删除**上一轮遗留的 `问题清单.md`（含旧名 `问题澄清.md`）。
- **中间分析（事实/矩阵/扫描/检查器）全在对话内，不落盘**；代码基线快照落 `${TMPDIR:-/tmp}/req-clarify-baseline`，不进交付物、不进版本库。
- 产物目录默认 `<当前终端目录>/req-clarify-out/`；产品只读交付物。

## 输入（三项必填 + 一项派生）

| 参数 | 必填 | 说明 |
|---|---|---|
| ① 项目地址（后端 + 前端，两个独立仓库根） | ✅ | 默认当前终端目录，但**必须经使用者确认才生效**；前端可标「无」并跳过该端基线 |
| ② 方案文档地址/路径 | ✅ | 本地文件（md/doc/docx/txt/pdf 文本）或可公开访问的 URL |
| ③ 取证分支（后端 + 前端） | ✅ | 后端默认 `master`（无则 `main`），前端同规则，**两端分别算** |
| 产物输出目录 | — | 默认 `<当前终端目录>/req-clarify-out/` |

**缺参数走 Stage -1 输入引导**（`AskUserQuestion` 逐项问，细则见 `references/input-collect.md`）。

**校验 repo**：路径存在、可读、确实是 git 仓库根、里面确实有源码。空目录/非代码库 → **只重问该项**并说清实测结果，**不许对着空目录编清单**。

## 代码基线：双仓各导一份，只在锁定的取证分支上取证

> **开发常忘记切分支** —— 工作区停在 feature 分支时，扫出的"现状"是中间态，一半"缺陷"是伪缺陷。默认 `master`/`main`，由使用者在 Stage -1 定夺；本次需求若正是某个 feature 分支上的开发，选它是合理的，但要说清"未提交改动不进基线"。

```bash
bash <skill目录>/scripts/prepare-baseline.sh <后端repo> [基线根目录] --branch <分支> --label 后端
bash <skill目录>/scripts/prepare-baseline.sh <前端repo> [基线根目录] --branch <分支> --label 前端
```

- 基线根默认 `${TMPDIR:-/tmp}/req-clarify-baseline`；实际路径 `<基线根>/<repo名>/<分支>-<提交>/tree-<分支>-<提交>/`，**内容寻址**（同一 `(repo,分支,提交)` 自动复用）。
- **导只读副本**：不切使用者工作区、不碰未提交改动。
- 三种情形**逐端独立判断、不猜**：**A** 分支存在且完整覆盖工作区源文件 → 用分支副本；**B** 分支存在但有源文件未被 git 跟踪 → 分支副本 + 补入工作区**未跟踪的 `src/` 源文件**（文档/图片/临时产物不补）→ **必须告知使用者**；**C** 分支不存在 → 直接用工作区 → **必须告知**。
- **从这一刻起，所有代码读取都指向基线目录，不指向工作区。**
- **分支与提交记进 `实现方案.md` 头部两行**（`后端：<路径>@<分支>@<提交>` / `前端：<路径>@<分支>@<提交>`）。`问题清单.md` 是给产品看的，**不放取证信息**。

## 核心模型：差集即缺陷

```
缺陷集 = 代码事实空间 − 方案意图空间
```

- **深度（覆盖矩阵）**：方案条目 × 代码事实，每格填三态 —— `✔` 已覆盖 / `✘` 明确不涉及 / `?` 未提及（= 缺陷候选）；每个 `?` 变成一条**方案疑点**。
- **广度（七维度扫描）**：新增物（类型/入口/字段/状态/规则/角色/渠道/配置）给系统加了**一个新的分流维度**；凡是**按它分流**或**被它影响**的存量功能都要表态 —— 波及但方案没提 = **方案遗漏**；确定不受影响 = **对话内留痕，不进交付物**。

**七个维度**：① 数据可见性 ② 行为分流 ③ 字段与校验 ④ 副作用 ⑤ 流程与时效 ⑥ 对外与集成 ⑦ 权限与配置（枚举方法见 `impact-inventory.md`）。

**代码事实六类**（全集抽取，每条带 `file:line`）：入口事实 / 类型事实 / 字段事实 / 流程事实 / 约束事实 / 副作用事实（方法见 `fact-extraction.md`）。

> 面向产品的产物里一律叫「方案疑点 / 方案遗漏」，不要暴露「深度 / 广度」；维度标注列统一叫「**影响维度**」。

## 执行流程（六阶段 + 一个分支点）

每阶段的放行门在对话内逐项核对，不许跳阶段口头带过。**Stage 5 是分支点**。

### Stage -1 · 输入引导（三项缺一不可）

三项输入收齐并**回显确认**才准进 Stage 0。顺序 **① 项目地址 → ③ 取证分支 → ② 方案地址**；`AskUserQuestion` 一轮最多 4 问；**已经给过的值一律不再问一遍**；草稿默认不落盘（用户明确要文件填才写，用完即删、不归档）。

### Stage 0 · 输入解析 + 迭代夹 + 双基线锁定

1. 校验方案可读（本地 `Read` / URL `WebFetch`）与两端 repo 有效。
2. 方案名（读方案后总结，≤12 字，去文件系统非法字符）→ 夹 `<产物目录>/<方案名> 迭代/`；夹已存在 → **本轮覆盖**，不新建。
3. 方案原文/原型/截图 `cp` 进 `产品方案/`（**保留原始文件名**）；需登录抓不到的**不落盘**，在对话里提示用户自行下载。
4. 跑 `prepare-baseline.sh` 锁双端基线，逐端读报告（分支+提交 / 基线目录 / 降级情形），**降级必须告知使用者**。
5. 读方案，在对话内拆成**可编号的需求条目**（改动对象 / 目标 / 是否含字段级描述）。
6. 圈定**作用域** —— 范围外的代码事实**不作为缺陷上报**。
7. 识别**新增物种类** → 决定 Stage 2 的重点维度。

### Stage 1 · 代码事实抽取

按六类事实逐一抽取，**要全集不要抽样**，每条带 `file:line` 证据，按端分节。可先跑 `scripts/survey.sh`（双仓各一次）做机械定位 —— 脚本只定位，判定由你做。

### Stage 2 · 七维度扫描（管广度）

逐维度问「新增的这批数据要不要影响它」：**有疑点** → 写成一条**方案遗漏**（问题 + 现状行为 + 可选解读 + 建议默认 + `file:line`）；**确定不受影响** → 对话内留痕（一句理由 + `file:line`），不写进交付物。同一根因合并成一项。

### Stage 3 · 覆盖矩阵构建（管深度）

行=代码事实、列=需求条目，**零空格**（三态见上）。矩阵在对话内构建，不落盘。

### Stage 4 · 检查器 + 疑点定级

跑 C1–C4（覆盖 / 一致 / 完备 / 流程等价，规则见 `checkers.md`）→ 每个 `?` 转成一条**方案疑点**；并入 Stage 2 的**方案遗漏**。

### Stage 4.5 · 提问价值自检（候选疑点 → 可交付问题）★路径 A 专属

覆盖矩阵与七维度保证「不漏」，**不保证「每条都值得问」** —— 掺进凑数问题会让产品对**整份文档**的可信度打折。每条候选过四道闸门 + 方案改写句测试：

| 闸门 | 判据 | 不过关的处置 |
|---|---|---|
| ① 产品拍得了吗 | 答完方案里会多出一句**业务规则**吗 | 降级为「给开发」备注 |
| ② 答案会改变方案写法吗 | 建议默认 = 维持现状 / 不需要 / 照搬存量 → 零信息量 | 降级为备注，并把下面的真问题捞出来改写 |
| ③ 能被另一条推导吗 | 依赖型、同主题 | 合并进相邻问题，不新增编号 |
| ④ 方案原文能读出来吗 | 已写明或读完即得 | 降级为背景事实 |
| ★ 方案改写句 | 「产品答完这句，方案里要改成哪一句？」 | 改不出来 → 丢弃 |

五种处置：**保留 / 改写 / 合并 / 降级为备注 / 丢弃**（丢弃的**在对话里留痕**：一句理由 + `file:line`，不进交付物）。面向产品的清单 **≤15 条**（硬上限 ~20）；超了先合并同主题、再砍低级别 —— 不砍高价值问题凑数，也不保留凑数问题。细则与翻车样本见 `references/issue-worth.md`。

### Stage 5 · 放行判定 ★分支点

**判定看的是自检后剩下的**：非空 → 路径 A；为空 → 路径 B。

**路径 A · 有疑点 → 产出问题清单**

1. 按 `templates/issue-list.md` 产出 `<夹>/问题清单.md`（**只留问题本身**：问题汇总表 + 每条问题）。
2. **沿革维护（不写进交付物）**：夹内已有旧版 → **先读**，与本轮候选逐条对比（哪些已答 / 未答 / 新增 / 剔除），对比结论以一段说明给使用者；旧文件读完即覆盖，旧名文件读完即删。
3. **证据自检（必做）**：

   ```bash
   bash <skill目录>/scripts/verify-citations.sh \
     --baseline <后端基线目录> --baseline <前端基线目录> -- <夹>/问题清单.md
   ```

   它打印每处引用指向的那一行并标注命中基线 —— **逐行核对语义是否对得上**（行号有效但指向相邻字段，校验器查不出来，只能人眼看）。
4. **自洽自检（必做）**：`bash <skill目录>/scripts/check-issue-list.sh <夹>/问题清单.md` —— 核对计数、级别分布、编号连续唯一、正文小节与汇总表一一对应、每条有「给产品」「给开发」两段、Q/REQ 交叉引用、交付物纯净度。**FAIL 必须清零才能交付**，WARN 逐条确认。
5. **暂停并交付** —— 产品**只读**这份清单，改完方案提交回来；**不产出实现方案.md**。交付时在对话里附本轮说明（沿革 + 自查：候选 N 条 → 交付 M 条，删/改/合各几条及理由），**这些说明不进交付物**。

**重跑**：产品提交新方案 → **复用同一夹** → 覆盖 `产品方案/` 与 `问题清单.md` → Stage 0~4.5 全重跑；基线按 `(repo,分支,提交)` 内容寻址自动复用。一次改稿常连带影响别处，矩阵与七维度都要重扫。**循环直到疑点清单为空** —— 高/中级必须清零；低级别可带默认建议进入路径 B，但要在实现方案的「不做清单」或「边界与异常」里写明。

**路径 B · 无疑点 → 直接产出实现方案**

不出问题清单（全是"无需调整"，对产品毫无价值）。进入 Stage 6；若夹内有上一轮遗留的 `问题清单.md`（含旧名 `问题澄清.md`）→ **删除它**（澄清轮次可浓缩成一句话并入实现方案追溯附录）。

### Stage 6 · 实现方案

按 `templates/implementation-plan.md` 产出 `<夹>/实现方案.md` —— **AI 照着它写代码，不需要再问任何问题**（含糊的代价会在下游兑现成猜测）。必须写到位：文件 + `file:line` + 锚点方法名 + 可照抄的改法；类名方法；DDL；接口契约；流程步骤与失败处理；**不做清单**；术语表；逐条验收标准；**存量功能结论落地对照**（每条方案遗漏与每条「无需调整」都要有落点，「无需调整」写明"沿用现有"）。**仍不产出代码。**

## 问题清单（交付物 A）

双层结构 —— 上层给产品、下层给开发：**上层一句话说清要产品回答什么，下层给证据、给选项、给默认建议**。

- **结构**：`问题汇总` 表（ID / 级别 / 一句话问题 / 来源 / 影响维度 / 方案对象）+ 逐条问题（`给产品（一句话）` → `为什么要问` → `给开发（证据与选项）`：代码证据 / 现状行为 / 可能解读 / 建议默认 /〔连带影响 / 风险提示 / 待产品补充〕→ `关联`），分「第一部分 · 方案疑点」「第二部分 · 方案遗漏」两段。模板见 `templates/issue-list.md`。
- **只留问题本身**：排查范围 / 免打扰清单 / 版本记录 / 基线信息 / 方案文档路径 **一律不写进交付物**（留在对话里）；被剔除的疑点在对话里留痕。
- **没有代码证据的问题不要提** —— 产品答不准，答不准等于没澄清。
- **不替产品做决策** —— 只列可选解读 + 标注建议默认，最终由产品改方案来定。
- **问题清单里不给技术方案** —— 讲"业务上这里该是什么"，不讲"建议这么改代码"。

## 实现方案（交付物 B）

模板 `templates/implementation-plan.md` + 硬性要求 `references/implementation-writing.md`。核心一条：**AI 照着它写代码，不需要再问任何问题。**

## 质量门（逐阶段卡口）

`G0` 输入可解析 ｜ `G1` 事实完备 ｜ `G1b` 扫描无盲区 ｜ `G2` 覆盖无空洞 ｜ `G3` 矛盾清零 ｜ `G4` 属性完备 ｜ `G5` 流程等价 ｜ `G8` 提问价值 ｜ `G9` 交付物自洽 ｜ `G6/G7` 实现方案自洽 / 可编码。

**任何一门未放行，不得进入下一阶段** —— 带着未澄清项进 Stage 6，等于把歧义直接喂给编码代理：它不会提问，会选一个"最合理的默认值"继续写。逐项判据见 `references/gates.md`。

## 红线

1. **代码库路径必须使用者确认**；默认值未经确认不生效，确认时回显两端最终路径。
2. **已给过的输入不再问一遍**（命令行参数 / 本轮对话里说过的都算）。
3. **取证分支默认 master/main，由使用者定**；选当前工作区分支要说清"未提交改动不进基线"；**所有代码读取指向基线目录**；降级情形必须写明。
4. **作用域外的代码事实不上报。**
5. **不问产品拍不了的技术细节**（排序 / 表名 / 命名 / 框架）—— 判据：答完方案里会多出一句业务规则吗？
6. **不问答案早已确定的问题**（建议默认 = 维持现状 / 照搬存量）—— 但要把下面的真问题捞出来改写。
7. **同一主题最多一条；依赖型问题不单独问。**
8. **每条问题必须能改写成方案里的一句话。**
9. **丢弃一条疑点 ≠ 把它抹掉** —— 对话内留痕（理由 + `file:line`）。
10. **交付前必跑两道机器校验**：引用校验 + 自洽校验，FAIL 清零。
11. **不替产品做决策。**
12. **方案无疑点就不出问题清单。**
13. **交付物只留问题本身**；问题清单是只读的，不设"产品答复"环节。
14. **不产出代码** —— 终点是 Markdown。

## 运行方式

```
/req-clarify                                              # 无参数 → 走 Stage -1 输入引导
/req-clarify <方案地址> --repo-backend <路径> --repo-frontend <路径> \
             [--branch <分支> | --branch-backend <分支> --branch-frontend <分支>] [--out <目录>]
```

带参数时跳过提问，参数直接作初值（`--repo-*` 视为使用者已确认），只问参数没覆盖到的项。

| 脚本 | 用途 |
|---|---|
| `scripts/scan-repos.sh` | Stage -1 扫候选仓库：绝对路径 / 端归属 / 当前分支 / 有无 master-main / 未提交数 |
| `scripts/prepare-baseline.sh` | 锁分支、导出只读副本、报告完整性与降级情形，内容寻址自动复用 |
| `scripts/survey.sh` | 机械定位六类事实的候选位置（`file:line` 线索），双仓各跑一次 |
| `scripts/verify-citations.sh` | 校验 `file:line` 引用是否存在并打印所指行：`--baseline <dir>`（双仓各一个）`-- <文档>` |
| `scripts/check-issue-list.sh` | 校验问题清单的内部自洽与纯净度：计数 / 级别分布 / 编号连续唯一 / 正文对齐 / 两段结构 / 交叉引用 / 纯净度 |

---

**交付前自查**：① `产品方案/` 含方案原文与原型原文件（原始文件名）② 两份交付物已落盘且另一份不存在 ③ 每处 `file:line` 过 `verify-citations.sh` ④ G0/G1/G1b/G2/G3/G4/G5/G8 全绿 ⑤ 出 `问题清单.md` 时 G9 全绿（`check-issue-list.sh` 零 FAIL）⑥ 出 `实现方案.md` 时 G6/G7 全绿、零 `TBD`、头部写了双端基线分支与提交。
