# 需求澄清：方案 × 代码库 → 问题清单 / 实现方案

## 定位

**这是一个需求澄清工具，只产出 Markdown 文档，不产出任何代码。**

输入：一份产品方案 + 一个代码库。
输出（**取决于方案有没有问题**）：

| 方案状态 | 产出 | 交给谁 | 下一步 |
|---|---|---|---|
| **有疑点** | **问题清单** —— 所有不完整、有疑问、缺失的地方，逐条带代码证据 | 产品 | 产品**改方案** → 提交新方案 → 重跑 |
| **无疑点** | **实现方案** —— 变更点、类名方法、表结构、验收标准俱全 | 开发 / AI 编码代理 | 直接编码 |

**方案没问题就不出问题清单。** 硬造一份问题单是噪音 —— 产品分不清哪些是真缺陷、哪些是凑数，反而降低了整份文档的可信度。

只有两个目的：**把方案澄清到无歧义**，以及**把实现依据写到位**。

不负责：写代码、给产品代做决策。

> **产品与澄清工具之间的交互只有一种：改方案。** 没有"填答复表"、没有"裁决"环节 —— 问题清单是**只读交付物**。

## 产物目录（只有 3 个交付物）

每个迭代夹只放 3 样东西，**交付物与工作稿彻底分离** —— 中间分析（事实抽取、覆盖矩阵、七维度扫描、检查器）全部在对话内完成，不落盘：

```
<产物目录>/                              # 默认 <当前终端目录>/req-clarify-out/
└── <方案名> 迭代/                       # 单夹，每轮覆盖（不分轮次编号）
    ├── 产品方案/                        # 上传的方案、原型等原文件（保留原始文件名）
    │   ├── xxxx 方案.md
    │   └── xxxx 原型.html
    ├── 问题清单.md                    # ★仅当有疑点（内部标 v1/v2/v3 版本）
    └── 实现方案.md                      # ★仅当无疑点（问题清单为空时才产出）
```

- **产品方案/** —— 产品上传的方案、原型等**原文件**，保留原始文件名，不做转化/重命名
- **问题清单.md** 与 **实现方案.md 二选一**，不会同时存在：
  - 有疑点 → 产出 `问题清单.md`，**不产出** `实现方案.md`；开发把问题清单发给产品
  - 无疑点 → 产出 `实现方案.md`，**删除**上一轮遗留的 `问题清单.md`（含旧版名称 `问题澄清.md`）
- 产品改方案后重跑 → **复用同一夹 `<方案名> 迭代/`**，覆盖 `产品方案/` 原文件、覆盖 `问题清单.md`（版本号 +1）。想保留某轮原文，使用者在改稿前自行复制

## 输入（三项必填 + 一项派生）

| 参数 | 必填 | 说明 |
|---|---|---|
| **① 项目地址**（前端 + 后端） | ✅ | 后端仓库根 + 前端仓库根（**两个独立仓库**）。默认取当前终端目录，但**必须经使用者确认才生效**。前端可标「无」并跳过该端基线 |
| **② 方案文档地址或路径** | ✅ | 产品的方案原文。本地文件（md / doc / docx / txt / pdf 文本均可），或可公开访问的 `http(s)` URL |
| **③ 取证分支**（后端 + 前端） | ✅ | 后端默认 `master`（该仓无则 `main`），前端同规则，**两端分别算**。只在哪个分支上取证 |
| 产物输出目录 | — | 默认 `<当前终端目录>/req-clarify-out/`，实际产物落到 `<产物目录>/<方案名> 迭代/`（单夹，每轮覆盖） |

**没有代码库就没有事实基线** —— 遗漏是相对于代码里真实存在的东西而言的，代码库猜错，整份问题单的可信度归零。**两份基线各自独立**：后端猜错毁后端结论，前端猜错毁前端结论。

**缺参数时的处理**：**不要自行假定，走 Stage -1 输入引导**（见下）—— 用 `AskUserQuestion` **逐项引导使用者输入**，缺哪项问哪项，**已经给过的不许再问**。细则见 `references/input-collect.md`。

**校验 repo**：路径存在、可读、确实是 git 仓库根、里面确实有代码（能找到源码文件）。是空目录 / 不是代码库 → **只重问该项**并说清实测结果，不要对着空目录编出一份"完整"的问题单。

## 代码基线：双仓各导一份，只在锁定的取证分支上取证

> **开发常常忘记切分支。** 工作区停在 feature 分支上时，扫出来的"现状"其实是**开发中间态** —— 新写的代码没提交、老代码已被改过、还有半成品重构。这时候澄清出来的"缺陷"有一半是伪缺陷：产品看到的是他自己刚改到一半的东西。**所以默认取 master / main** —— 但本次需求若正是某个 feature 分支上的开发，当前分支才是真实上下文，由使用者在 Stage -1 定夺。

**规则：所有代码事实一律来自 Stage -1 锁定的取证分支（默认 `master` / `main`，可由使用者显式指定当前工作区分支），与工作区当前在哪个分支无关。前后端两个仓库各自独立锁定、各自导副本。**

**做法：导出一份只读副本，全程在副本上作业** —— 不切使用者的工作区，不碰他的未提交改动，也不要求他记得切分支。后端、前端各导一份：

```bash
bash <skill目录>/scripts/prepare-baseline.sh <后端repo> [基线根目录] --branch <后端分支> --label 后端
bash <skill目录>/scripts/prepare-baseline.sh <前端repo> [基线根目录] --branch <前端分支> --label 前端
```

`[基线根目录]` 省略时默认 `${TMPDIR:-/tmp}/req-clarify-baseline`。**基线不落在产物目录里** —— 产物目录只放 Markdown，代码快照既不进交付物、也不进版本库。

**实际路径**：`<基线根目录>/<repo名>/<分支>-<提交>/tree-<分支>-<提交>/`

内容寻址 —— 同一 `(repo, 分支, 提交)` 永远落在同一路径，**自动复用**，不需要指定"上一迭代的基线目录"。导出只要 0.2 秒（后端 41MB / 前端 7MB），专门维护一套复用传参机制不值得。

每端各自判断三种情形，**不猜**（两端可能情形不同，比如后端 A、前端 B）：

| 情形 | 判定 | 基线 | 必须告知使用者 |
|---|---|---|---|
| **A** | 所选分支存在，且其内容完整覆盖工作区源文件 | 该分支的导出副本 | 否 |
| **B** | 所选分支存在，但有源文件**未被 git 跟踪** | 分支副本 + 补入工作区未跟踪源文件 | **是** —— 该分支不是完整基线 |
| **C** | 所选分支不存在（无 master/main / 无提交 / 非 git 仓库） | 直接用工作区 | **是** —— 证据取自工作区，工作区不对结论就失真 |

**情形 B 常见于"源码没纳入 git 管理"的仓库** —— 例如只提交了后端 `.java`、前端 `.vue`/`.js` 全是未跟踪状态。这种情况下 `git archive` 会把整个前端悄悄丢掉，必须补回来并明确标注。

**补入范围已收紧：只补 `src/` 下的源文件**（`.java/.vue/.js/.ts/.xml/.sql/.json` 等）。文档、图片、临时产物（如 `*.puml`、`.playwright-mcp/*.yml`、`img/`）**不是"现状"**，补进来只会污染基线 —— 工作区里这些多半是本地产物，把它们当成主干事实会误导结论。

**分支与提交必须记进两份交付物的头部，分两行**：
- `后端：<路径>@<分支>@<提交>`
- `前端：<路径>@<分支>@<提交>`

某端缺失则写 `前端：无（本次仅后端）`；情形 C 写成 `后端：<路径>@<工作区现状（所选分支不存在）>`。

**后续所有读取都指向基线目录，不指向工作区** —— 后端事实指向 `<基线根>/<后端repo名>/<分支>-<提交>/tree-*`，前端事实指向 `<基线根>/<前端repo名>/<分支>-<提交>/tree-*`。

## 核心模型：差集即缺陷

> 方案 = 意图（不完备、内部可能自相矛盾）
> 代码 = 现状事实（完备、可验证、可追溯）

**澄清不是"读懂方案"，是求差集：**

```
缺陷集 = 代码事实空间 − 方案意图空间
```

四类痛点都是差集的不同表现，**一个机制（覆盖矩阵）覆盖全部四类**：

| 痛点 | 差集形式 | 矩阵表现 | 检查器 |
|---|---|---|---|
| 功能描述遗漏 | 事实存在，方案无条目命中 | **空格** | C1 覆盖 |
| 前后相互矛盾 | 两条意图对同一事实给出互斥值 | **冲突格** | C2 一致 |
| 描述过于简洁 | 条目命中对象但属性未给全 | **半填格** | C3 完备 |
| 流程节点遗漏 | 现状节点无对应方案条目 | **流程空格** | C4 流程等价 |

> 覆盖矩阵、六类事实抽取、检查器判定**全部在对话内完成**，不落盘成文件。事实记录格式、矩阵三态、检查器规则见 `references/`。

## 第二条主线：广度

**新增一个类型 / 入口 / 字段 / 状态 / 规则，不是"加一个东西"，而是给系统加了一个新的分流维度。**

> 凡是**对这个维度分流**、或**受这个维度影响**的存量功能，都必须表态：新东西来了，它要不要跟着变？

产品最常犯的错不是"改错了"，而是**"没想到要改"**。方案只写新东西怎么实现，存量功能一个字不提 —— 五个按钮共用一个查询入口、导出走另一条 SQL、统计按状态 count、定时任务按状态扫、对外 API 暴露了类型枚举…… 每一条都会漏。

**这一类问题不能靠"问几个问题"解决，要靠一次系统性的扫描。** 七个维度逐个扫，扫完的结论全部落进交付物（有问题 → 问题清单；无疑点 → 实现方案的「存量功能结论落地对照」）：

```
覆盖矩阵  → 管「深度」：这一类里每一条细节准不准
七维度扫描 → 管「广度」：有没有漏掉一整类功能
```

**两条线问的不是同一件事，所以都要做 —— 但它们不是两类问题，是两种问法：**

| | 问的问题 | 结论是什么 |
|---|---|---|
| 覆盖矩阵 | 方案**有没有提到**这个事实 | 提到但没说全 / 矛盾 → **方案疑点** |
| 七维度扫描 | 这个存量功能**会不会被波及** | 波及但方案没提 → **方案遗漏**；不受影响 → 计入排查范围声明 |

**七维度扫描是产出「方案遗漏」的方法，不是第三类问题。** 交付物里只有「方案疑点 + 方案遗漏」两类 —— 扫描在对话内完成，结论直接落进交付物的「排查范围」表。

它独有的两样东西：① **完整性 checklist** —— 七个维度是"扫全了"的闭集定义（尤其覆盖事实抽取容易漏掉的展示类入口、权限配置类点位）；② **「无需调整」免责结论** —— 覆盖矩阵只记录对不上的地方，没有地方记录"查过了、不受影响"。

扫描维度、代码枚举方法、常见漏盘点的地方，见 `references/impact-inventory.md`。

## 为什么必须读代码

纯读方案永远只能发现"方案自相矛盾"，发现不了"方案没提的"。因为**遗漏是相对于代码里真实存在的东西而言的**。

代码事实至少有六类（不是"业务流程 vs 功能描述"两类，分类要更细才能定位）：

1. **入口事实** — 页面/接口上所有操作入口及其背后动作（按钮、菜单、API）
2. **类型事实** — 业务类型枚举的**全部取值**，以及每个取值触发的差异化分支
3. **字段事实** — 涉及对象的**完整字段集**，及每个字段的**所有写入路径**
4. **流程事实** — 状态集合 + 状态流转边 + 每条边的守卫条件与副作用
5. **约束事实** — 校验规则、默认值、权限点
6. **副作用事实** — 发消息、写日志、建任务、调第三方、对账等

> **新增一个类型 → 最危险的是类型事实中的"差异化分支"**。代码里凡有 `switch(type)` / `if (type == X)` 的地方，新增类型都要落到某个分支上。方案通常只说新类型自己的分支，漏掉"老分支要不要排除新类型"。

抽取方法与检索模式见 `references/fact-extraction.md`。

## 执行流程（输入引导 + 六阶段 + 一个分支点）

每个阶段的**放行门**在对话内逐项核对，不允许跳阶段口头带过。
**Stage 5 是分支点** —— 方案有没有问题，决定后面产出问题清单还是实现方案。

### Stage -1 · 输入引导（三项缺一不可，未确认不得进入 Stage 0）

**每次运行都要先过这一关 —— 不管有没有参数。** 三项必填输入收齐并回显确认，才准进 Stage 0：

| # | 输入 | 组成 | 缺省 | 校验 |
|---|---|---|---|---|
| ① | **项目地址** | 后端仓库根 + 前端仓库根（两个独立仓库） | 当前终端目录 | 存在 → 是 git 仓库根 → 含源码 |
| ② | **方案地址** | 本地路径 或 `http(s)` URL | 无（必填） | 可读 / URL 抓得到正文 |
| ③ | **取证分支** | 后端分支 + 前端分支 | `master`，该仓无则 `main` | 该分支在对应仓库存在 |

**流程**：

1. **取当前终端目录**：`pwd`。
2. **扫环境**（做预填，不做默认）：
   ```bash
   bash <skill目录>/scripts/scan-repos.sh <当前终端目录>
   ```
   输出每个候选仓库的绝对路径、端归属、当前分支、有无 master/main、有无提交、未提交文件数。
   **前端须命中真实前端框架依赖才算前端仓** —— 多仓工作区根常放空壳 `package.json` 当骨架，把它当作前端仓会扫出一堆假事实。
3. **判定哪些要问**：来源优先级 **命令行参数 > 本轮对话已说 > 环境扫描 > 问**。`--repo-backend` / `--repo-frontend` 视为使用者已确认，不再问。**已给过的值一律不再问一遍** —— 只问真正缺失的项，重复问已答项是噪音。
4. **按 ① → ③ → ② 顺序问**（`AskUserQuestion`，一轮最多 4 个问题；缺项超 4 个时按此顺序分批，每批问完先回显一次）：
   - **① 项目地址** —— options 的 label 写**绝对路径**（使用者要拿去填参数），description 附当前分支 / 有无 master-main / 是否空仓库；候选多于 3 个时只列 3 个最可能的；「其他」永远保留；前端保留「无（本次仅后端）」
   - **③ 取证分支** —— 默认值**逐端算**（前端常只有 `main`）；options 给「确认 master/main」与「当前工作区分支」两条 +「其他（后端:xxx 前端:yyy）」
   - **② 方案地址** —— options 给候选文档 /「逐个列标题让我选」/「其他（路径或 URL）」
5. **校验每一项**：不合格的**只重问那一项**，说清「哪一项不合格 + 实测结果」。**不许将就** —— 不要对着空目录编出一份"完整"的问题单。
6. **回显六项**（方案地址、后端路径、前端路径、后端分支、前端分支、产物目录）供使用者核对，标注每项来源。**回显后才进入 Stage 0。**

**详细问法、options 构造规则、多仓场景取值、校验回退话术**，见 `references/input-collect.md`。

**草稿文件默认不写** —— 表单只渲染在对话里（v3.2.0 起过程不落盘）。使用者明确要文件填（说「给我个文件填」）才写 `<当前终端目录>/req-clarify-input.md`，用完即删、**不归档进交付物夹**。

**带参数运行时的处理**：`/req-clarify <方案地址或路径> --repo-backend <后端路径> --repo-frontend <前端路径> [--branch <分支> | --branch-backend <后端分支> --branch-frontend <前端分支>] [--out <目录>]` —— 参数直接作为初值（`--repo-*` 给出的路径视为**使用者已确认**），**只问参数没覆盖到的项**，其余流程完全一致。

### Stage 0 · 输入解析 + 迭代夹 + 双基线锁定
1. 校验输入：方案文档可读（本地路径 → `Read`；`http(s)` URL → `WebFetch` 抓正文，抓不到或需登录 → 回头问使用者要本地文件）、后端/前端代码库路径有效（见上方「输入」）。两端其一标「无」时跳过该校验。
2. **确定迭代夹**（单夹、每轮覆盖，不分轮次编号）：
   - **方案名**：读方案后总结一个短名（中文可，去掉 `/` `\` `:` `*` `?` `"` `<` `>` `|` 等文件系统非法字符，限 ~12 字）。例如方案《订单类型扩展方案》→ `订单类型扩展`。
   - **夹路径**：`<产物目录>/<方案名> 迭代/`。扫描 `<产物目录>/` 下是否已有该夹：**有 → 本轮覆盖该夹**（产品提交了新方案版本）；**无 → 新建**。不再有 `迭代1/迭代2/迭代3` 这类轮次后缀。
   - **同轮重跑**：使用者未提供新方案版本、只是续跑（断点继续/补产物）→ 复用已有夹，不新建。
3. **产品方案原文件落盘**（让夹子自包含、可追溯）：
   - 方案文档 / 原型 / 截图统一落到 `<夹>/产品方案/`，**保留原始文件名**，不做转化、不重命名、不转码（doc/docx/pdf 维持原格式）：
     - 本地文件 → `cp` 进 `<夹>/产品方案/<原文件名>`
     - 公开 URL → 下载进 `<夹>/产品方案/<原文件名或推导名>.<ext>`
   - 方案里引用的 `![](...)`、`附件:`、Figma/墨刀链接等 → 本地路径 `cp` 进 `<夹>/产品方案/`，公开 URL 下载进同目录；需登录/抓不到的**不落盘**，在对话里提示使用者在对话里用 `! <命令>` 跑下载或贴本地路径。
4. **锁定双代码基线**（见上方「代码基线」）：

```bash
# 基线落在缓存目录，不进产物目录；同一 (repo, 分支, 提交) 自动复用
BASELINE_ROOT="${TMPDIR:-/tmp}/req-clarify-baseline"

bash <skill目录>/scripts/prepare-baseline.sh <后端repo> "$BASELINE_ROOT" --branch <后端分支> --label 后端
bash <skill目录>/scripts/prepare-baseline.sh <前端repo> "$BASELINE_ROOT" --branch <前端分支> --label 前端
```

   逐端读报告，确认三件事：**基线分支 + 提交号**、**基线目录**、**是否有降级情形**。两端各自判断、各自告知：
   - 某端情形 B / C → **必须把该端的降级事实告诉使用者**（"后端分支不是完整基线" / "前端证据取自工作区现状"），并请他确认该端工作区就是主干代码。
   - 情形 A → 该端直接往下走，不必打扰使用者。
   - **从这一刻起，所有代码读取都指向两份基线目录，不指向工作区。**
5. 读方案文档，在对话内拆成**可编号的需求条目** `REQ-001...`，每条标注：改动对象、目标、是否含字段级描述。
6. 判断方案是否可解析（见 G0）。方案过于零散时，先按"对象"重组成条目。
7. 明确本次改动**作用域**：哪些模块/页面/接口在范围内。作用域之外的代码事实**不作为缺陷上报**（见下方红线）。
8. **识别本次新增物的种类**（类型 / 入口 / 字段 / 状态 / 规则 / 角色 / 渠道 / 配置）—— 决定 Stage 2 的重点维度。

**不单独落盘产物** —— 需求条目、新增物种类、基线两行信息在对话内持有；基线分支与提交两行后续写进 `问题清单.md` / `实现方案.md` 的头部。

### Stage 1 · 代码事实抽取
按六类事实逐一抽取，**要全集，不要抽样**。每条事实带 `file:line` 证据。事实记录格式（F-xxx）见 `references/fact-extraction.md`。

**所有读取都基于 Stage 0 锁定的两份基线目录** —— 不是工作区。后端事实从 `<基线根>/<后端repo名>/<分支>-<提交>/tree-*` 取、前端事实从 `<基线根>/<前端repo名>/<分支>-<提交>/tree-*` 取；按端分节，每条证据标注来源端。

建议先跑 `scripts/survey.sh` 做机械线索定位（脚本只定位，判定由你做）—— **双仓各跑一次**：

```bash
bash <skill目录>/scripts/survey.sh <基线根>/<后端repo名>/<分支>-<提交>/tree-* --label 后端
bash <skill目录>/scripts/survey.sh <基线根>/<前端repo名>/<分支>-<提交>/tree-* --label 前端
```

**不单独落盘产物** —— 六类事实在对话内持有，供 Stage 2/3/4 取用。

### Stage 2 · 七维度扫描（管广度）
把 Stage 1 的事实按**七个维度**归类，逐条问"新增的这批数据，要不要影响它"：

| 维度 | 问什么 |
|---|---|
| ① 数据可见性 | 在哪些地方出现 / 不出现（列表、**导出**、统计、待办、消息、对外查询）；**反向必做**：方案声明的产出物/返回值（条码、回单号、外部回写号）在列表/明细/导出有没有字段落点 |
| ② 行为分流 | 走哪条分支（switch/策略/状态机/**兜底分支**）；**纵向必做**：每个操作入口/按钮背后的可选范围、批量/单条、入参（前端传什么/后端补什么）、目标页面是否定义 |
| ③ 字段与校验 | 字段怎么填、校验要不要变（默认值、非空、唯一、上限） |
| ④ 副作用 | 会不会触发（MQ、消息、日志、任务、**额度/积分/库存**、第三方、对账） |
| ⑤ 流程与时效 | 走哪条流程、时限变不变（超时、自动流转、驳回清理） |
| ⑥ 对外与集成 | 对外暴露成什么样、**下游要不要适配** |
| ⑦ 权限与配置 | 要不要单独的权限 / 开关 / 白名单 |

每个维度扫完，结论只有两种去处：

- **有疑点** → 写成一条**方案遗漏**（见问题清单结构）
- **确定不受影响** → 计入问题清单「排查范围」表的「确认不受影响」列，**带一句理由**

> **走路径 B（无疑点）时**，落点换成 `实现方案.md` 的「存量功能结论落地对照」表 —— 此时「需澄清」应为空，全部是已落地的改动项或「沿用现有」的显式声明。

扫描方法见 `references/impact-inventory.md`。

**规则**：
- 同一根因合并成**一项**（5 个按钮共用一个查询 = 1 条疑点，不是 5 条）
- **「不受影响」也要显式写出来** —— 它是免责证据，也是让产品知道"这里查过了"的凭据
- 每条都必须带 `file:line`，没证据的不写

### Stage 3 · 覆盖矩阵构建（管深度）
行 = 代码事实，列 = 需求条目。**在对话内构建**（不落盘）。

**每个格子必须填三态之一**，空格不允许存在：
- `✔` 方案已覆盖且无歧义
- `✘` 方案明确说不涉及（也算覆盖，带理由）
- `?` 方案未提及 → **缺陷候选**

三态与判定规则见 `references/checkers.md`。

### Stage 4 · 检查器 + 疑点定级
对矩阵跑 C1–C4 检查器（规则见 `references/checkers.md`），每个 `?` 格转成一条**方案疑点**；再把 Stage 2 的方案遗漏并进来。**在对话内汇总疑点清单**，不落盘。

### Stage 4.5 · 提问价值自检（候选疑点 → 可交付问题）★路径 A 专属

> **覆盖矩阵和七维度扫描保证「不漏」，不保证「每条都值得问」。**
> 掺进 5 条"产品答不了 / 答案早已由代码决定"的问题，会让产品对**整份文档**的可信度打折 —— 他分不清哪条是真缺陷、哪条是凑数。
> 所以疑点**不能直接写成问题**，必须先过这一关。

把 Stage 4 汇总的疑点列成**候选表**（候选问题 | 来源 | 建议默认 | 建议处置），逐条过四道闸门 + 一道测试：

| 闸门 | 判据 | 不过关的处置 |
|---|---|---|
| ① **产品拍得了吗** | 答案改完后，方案里会多出一句**业务规则**吗？不会 → 是技术细节（排序 / 表名 / 命名 / 框架） | 降级为「给开发」备注 |
| ② **答案会改变方案写法吗** | 建议默认 = 维持现状 / 不需要 / 照搬存量 → 零信息量 | 降级为「给开发」备注；**并把它下面的真问题捞出来改写** |
| ③ **答案能被另一条推导吗** | 依赖型问题（答了 A 就锁死 B）、同主题（留痕 / 导出 / 权限各拆一条） | 删除 / 合并进相邻问题 |
| ④ **方案原文能读出来吗** | 方案已写明或读完就能得出 | 降级为背景事实 |
| ★ **方案改写句** | "产品答完这句，方案里要改成哪一句？"—— 改不出来 → 这问的不是方案，是实现 | 降级为备注 / 丢弃 |

**五种处置，没有"丢了就不管"**：保留（Q-xxx）｜改写｜合并（并入相邻问题，不新增编号）｜降级为「给开发」备注 / 风险提示｜丢弃（落到「排查范围」的"确认不受影响"或"作用域外"，**留痕但不占额度**）。

**额度**：面向产品的清单建议 **≤ 15 条**（硬上限 ~20）。超了先合并同主题，再砍低级别 —— **不要砍高价值问题去凑数，也不要保留凑数问题**。

**自查说明**：定稿后把"候选 N 条 → 交付 M 条，删/改/合各几条及理由"写成一段说明**在对话里给使用者**（不必进产品文档），避免下一轮又长回来。

细则与真实翻车样本见 `references/issue-worth.md`。

### Stage 5 · 放行判定 ★分支点

**判定规则**：Stage 4.5 自检后**保留下来的候选问题**非空 → 路径 A；**为空** → 路径 B。

> 判定看的是**自检后剩下的**，不是原始疑点数 —— 全被降级为备注/丢弃，说明方案本身没有待产品拍板的歧义，应当直接产出实现方案（路径 B），而不是给产品一份"其实没什么要问"的清单。

#### 路径 A · 有疑点 → 产出问题清单

1. 按 `templates/issue-list.md` 产出 `<夹>/问题清单.md`（双层结构 + 排查范围表）
2. **版本沿革机制**（每轮覆盖同一夹，靠版本记录承载沿革）：
   - 写之前若夹内已有 `问题清单.md`（或旧版遗留的 `问题澄清.md`）→ 先读出其「版本记录」段，版本号 +1（v1 → v2 → …）；旧版名称的文件读完后删除，避免与新文件并存
   - 在版本记录表追加一行：版本 | 日期 | 本轮提疑点数 | 产品改稿要点（从新方案与上一版对比得出）| 剩余疑点数
   - 再写新版覆盖旧文件
3. **证据自检（必做）** —— 传两份基线，对 `问题清单.md` 一份跑（它自带全部 file:line 证据）：

```bash
bash <skill目录>/scripts/verify-citations.sh \
  --baseline <基线根>/<后端repo名>/<分支>-<提交> --baseline <基线根>/<前端repo名>/<分支>-<提交> \
  -- <夹>/问题清单.md
```

   它会输出每一处引用指向的那一行内容，并标注命中的基线（`[后端@master-d1b127a03]` 形式，端 + 版本一目了然）—— **逐行核对语义是否对得上**。
   行号有效但指向相邻字段的情况，校验器查不出来，只能靠人眼看预览。只有一端时只传一个 `--baseline`。

4. **自洽自检（必做）** —— 计数、编号、交叉引用、基线标识是人眼最容易漏、读者却一眼就发现的错（"说 19 条其实 18 条"、"合计 20 处但只列 18 条"）。一处错足以让产品怀疑整份文档的严谨度：

```bash
bash <skill目录>/scripts/check-issue-list.sh \
  [--baseline <基线根>/<后端repo名>/<分支>-<提交>] [--baseline <基线根>/<前端repo名>/<分支>-<提交>] \
  -- <夹>/问题清单.md
```

   它会核对：头部「待澄清 N 条（高 x / 中 y / 低 z）」、「怎么用」段与「下一步」段的三个数字、版本记录的「本轮提疑点数 / 剩余」、Q 编号连续性、排查范围表每行「需要改处数」== 该行「对应问题」条数、合计行 == 各行之和、免打扰清单条数 == 合计「确认不受影响」、全文 Q-xxx / REQ-xxx 引用可对上、基线行是否写成 `路径@分支@提交`。
   **FAIL 必须清零才能交付**；WARN 要逐条确认。

5. **流程到此暂停并交付** —— 产品**只读**这份问题清单，改完方案提交回来。**不产出 `实现方案.md`**。
   交付时在对话里附上**本轮自查说明**（候选 N 条 → 交付 M 条，删/改/合各几条及理由），让使用者知道哪些疑点是被有意剔除的、为什么。

**重跑**：产品提交新方案 → **复用同一夹 `<方案名> 迭代/`**，覆盖 `产品方案/` 原文件、覆盖 `问题清单.md`（版本号 +1）。Stage 0 ~ Stage 4.5 全部重跑。基线按 `(repo, 分支, 提交)` 内容寻址自动复用 —— 提交号没变就是同一个目录，不重导。
一次改稿常常连带影响别处：新类型的定义变了，七个维度要重扫，矩阵里所有格子也要重看。

**循环直到疑点清单为空。** 高/中级疑点必须清零；低级别疑点允许带默认建议进入路径 B，但要在实现方案的「不做清单」或「边界与异常」里写明。

#### 路径 B · 无疑点 → 直接产出实现方案

**不出问题清单。** 方案没问题，问题单里全是"无需调整"，对产品毫无价值。

进入 Stage 6。若夹内有上一轮遗留的 `问题清单.md`（或旧版名称 `问题澄清.md`）→ **删除它**（其版本记录可浓缩成一句话并入实现方案追溯附录，如"历经 v1..vN 共 N 轮澄清后定稿"）。

### Stage 6 · 实现方案
按 `templates/implementation-plan.md` 产出 `<夹>/实现方案.md` —— 一份**AI 可参照直接完成编码**的实现依据。

**必须写到位**：改哪个文件、改哪一处、改成什么（变更点行号 + 锚点方法名）、类名方法、表结构 DDL、枚举取值、接口契约、流程与失败处理、逐条验收标准。

**仍不产出代码** —— 给的是改动指令与关键片段，不是完整实现类。

**追溯附录必须含「存量功能结论落地对照」**：每一条方案遗漏、以及每一条「无需调整」，都要在实现方案里有落点。**「不受影响」也要写出来**（写明"沿用现有"）—— 否则无法验证每个结论都落地了。

**产物**：`<夹>/实现方案.md`

## 问题清单：双层结构

这是**路径 A 下的主交付物**。一份文件同时给产品和开发看：上层给产品，下层给开发。

```
### Q-007 [高] 新类型在「待审核」列表中是否可见

**给产品（一句话）**
新类型订单要不要出现在原有五个按钮的列表里？

**给开发**
- 证据：`src/service/orderService.ts:88`（五个按钮共用同一查询入口 queryOrders）
- 现状：五个按钮的过滤条件只按 status 区分，未按 type 区分；新增 type=T 后会出现在全部五个列表
- 可能解读：
  1. 老列表一律排除 type=T（需在共用入口加过滤，影响五个按钮）
  2. 老列表保留 type=T（无需改动）
- 建议默认：解读 1 —— 因为老列表的操作按钮对 T 不适用
```

**没有代码证据的问题不要提** —— 产品会答不准，答不准就等于没澄清。

**每条问题还要过一遍「提问价值自检」** —— 覆盖矩阵与七维度扫描保证**不漏**，不保证**每条都值得问**。技术细节（排序 / 表名 / 命名）、答案早已确定（建议默认 = 维持现状）、能被另一条推导出来（依赖型）、同主题重复（留痕 / 导出 / 权限各拆一条）的，一律**降级为「给开发」备注或合并**，不进汇总表。判据与处置见 `references/issue-worth.md`。

**「给开发」段承担两类内容**：① 这条问题的代码证据与可选解读；② **本轮被剔除但值得留痕的技术事实 / 风险提示**（数据归属、排序取舍、日志现状、"一个仓内混放多供应商"这类风险）—— 它们对开发有用，但**不该占用产品的澄清额度**。

**「排查范围」表兼作丢弃台账** —— 被剔除的疑点落到"确认不受影响"或"作用域外"，保证"扫过的都有结论"，同时不占额度。

**问题清单是只读的**：没有"答复记录"表、没有"已裁决"状态。产品读完直接**改方案**，改完提交回来重跑。

问题单分两部分，**标题用产品看得懂的说法**：

- **第一部分 · 方案疑点** —— 来自覆盖矩阵（方案条目 × 代码事实）。方案**已经写了**的那条要求，本身没说全、前后矛盾、或与代码对不上。
- **第二部分 · 方案遗漏** —— 来自七维度扫描（存量功能 × 新增物分流维度）。方案**完全没提**、但会被本次新增物波及的存量功能。

两者共用同一套结构、按同一套级别排序，产品只看一份清单。

**版本记录段**（夹子每轮覆盖，靠它承载沿革）：表格列 `版本 | 日期 | 本轮提疑点数 | 产品改稿要点 | 剩余`，每轮重跑追加一行。第 1 轮写 v1；产品改稿后重跑写 v2，依此类推。

> 内部术语仍叫「深度」（覆盖矩阵管深度）与「广度」（七维度扫描管广度）；**面向产品的产物里一律用「方案疑点 / 方案遗漏」**，不要把「深度 / 广度」暴露给产品。
> 汇总表的「来源」列取值随之写成 `方案疑点` / `方案遗漏`；维度标注列统一叫「**影响维度**」（深度来源的问题同样带维度标注）。

详见 `templates/issue-list.md`。

## 质量门（逐阶段卡口）

| 门 | 阶段 | 放行条件 |
|---|---|---|
| **G0** 输入可解析 | 0 | 三项输入（项目地址 / 方案地址 / 取证分支）已收齐并回显确认，**已给过的值不重复问**；方案条目已编号；每条有改动对象；作用域已圈定；新增物种类已识别；**后端/前端代码库路径均已确认有效**（标「无」的一端跳过）；**两份基线分支已锁定（默认 master/main，由使用者确认；可显式指定当前工作区分支），基线目录已生成，降级情形分端如实告知**；**迭代夹已建**（单夹 `<方案名> 迭代/`，每轮覆盖，无轮次后缀）；**产品方案/ 已落原文件** |
| **G1** 事实完备 | 1 | 六类事实均已抽取（对话内）；每类有"全集"声明（枚举全、字段全、节点全） |
| **G2** 覆盖无空洞 | 3 | 矩阵**零空格**（对话内）；每个 `?` 都有对应疑点 |
| **G3** 矛盾清零 | 4 | 方案内部无自相矛盾；与代码事实的矛盾已在方案里被修正，无悬空冲突；改稿要点写进问题清单版本记录 |
| **G4** 属性完备 | 4 | 无半填格：要么补全赋值，要么标注"不修改" |
| **G5** 流程等价 | 4 | 现状节点与方案节点一一映射；差异节点在方案中已说明 |
| **G1b** 扫描无盲区 | 4 | 七个维度均已扫过；每条方案遗漏与每条"无需调整"都带 `file:line` |
| **G8** 提问价值 | 4.5 | 每条候选疑点都过了四道闸门 + 方案改写句测试；每条都有明确处置（保留/改写/合并/降级备注/丢弃）；**丢弃的已落到排查范围表留痕**；清单条数 ≤ 15（硬上限 20）；依赖型问题已合并；同主题最多一条 |
| **G9** 交付物自洽 | 5 | `check-issue-list.sh` 全绿：头部/正文/版本记录三处计数一致、Q 编号连续、排查范围「需要改处数」==「对应问题」条数、合计 == 各行之和、免打扰清单条数 == 合计、Q/REQ 引用可对上、基线行 = 实际基线提交号 |
| **G6** 文档自洽 | 6 | 实现方案零未决项、零内部矛盾、零隐含假设；**存量功能结论每条有落点** |
| **G7** 可编码性 | 6 | 每个改动项都有 `file:line` + 锚点方法名 + 可照抄的改法；枚举变更列全所有同名位置；流程每步有失败处理；验收标准逐条可执行；零 `TBD`/`待确认` |

细则见 `references/gates.md`。**任何一门未放行，不得进入下一阶段** —— 带着未澄清项进 Stage 6，等于把歧义直接喂给编码代理：它不会提问，会选一个"最合理的默认值"继续写。

## 实现方案写作规范

实现方案的第一读者是**AI 编码代理**。它只有一个要求：

> **AI 照着它写代码，不需要再问任何问题。**

AI 遇到空白不会停下，它会继续编。所以**含糊的代价在下游兑现** —— 方案里省下的一句话，会变成下游的一次猜测。

细则见 `references/implementation-writing.md`，硬性要求：

1. **每个改动项定位到「文件 + `file:line` + 锚点方法名」** —— 只给行号，改动后行号漂移，会改到隔壁方法
2. **每个改动项给出可照抄的改法** —— 代码片段或明确步骤，不是"加个判断"
3. **枚举变更列全所有同名位置** —— 后端 `ReturnConst` 与 `Const`、前端 `ENUM.js` 多处，改一处漏一处就有的页面看不到
4. **表结构给 DDL**；字段用表格列全（类型 / 取值 / 何时写 / 为空时行为），并说明"未列出的字段"
5. **接口契约列全入参出参**，无"同上"
6. **流程用步骤表，每步都有失败处理**；定时任务给间隔 / 逻辑 / 完结条件 / 失败策略
7. **必须有「不做清单」** —— 不写，AI 会顺手把方案里"待沟通""后续迭代"的接口也实现了
8. **必须有术语表** —— 同一概念多个名字会造出两套实现
9. **逐条验收标准** —— 写清「操作」和「预期」，覆盖异常路径
10. **存量功能结论落地对照** —— 每条都有落点，「无需调整」写明"沿用现有"

> **仍然不产出代码。** 给的是改动指令与关键片段，不是完整实现类。

## 红线

- **后端、前端代码库路径都必须由使用者确认。** 默认值是当前终端目录，但**未经确认不生效**，也不能静默沿用。确认时把两条最终路径都回显一遍。两端各自猜错各自毁该端结论。
- **已经给过的输入不再问一遍。** 命令行参数、本轮对话里说过的路径 / 分支 / 方案地址 —— 直接采用并在回显时标来源，不重复追问。**只问真正缺失的项**：重复问已答项是噪音，使用者会以为 skill 没听懂，整轮体验崩掉。
- **取证分支默认 master / main，但由使用者定。** 开发常忘记切分支，工作区停在 feature 上时，扫出的"现状"是开发中间态，澄清出的缺陷有一半是伪缺陷 —— 所以默认推 master/main。但本次需求若正是某个 feature 分支上的开发，当前分支才是真实上下文，**选它是合理的**：必须把风险说清（工作区未提交改动不进基线、「现状」是分支提交态而非本地此刻），但**不替使用者否决**。分支选定后，**所有代码读取都指向 Stage 0 锁定的两份基线目录，不指向工作区。** 后端/前端基线分支与提交分两行写进两份交付物的头部。某端降级到工作区时（无 master/main），**必须在交付物里写明「该端证据取自工作区现状」**，不能让读者以为那是主干代码。提交号没变就是同一个基线槽位，自动复用；降级情形（B/C）不复用。
- **作用域外的代码事实不上报。** 一个老模块的字段缺口和产品本次需求无关，混进去会毁掉问题单的可信度。判定规则见 `references/checkers.md`。
- **不问产品拍不了的技术细节。** 排序规则、表结构/落库位置、字段/权限码命名、日志框架 —— 这些是开发的活。产品能拍板的是**业务规则**：流程走向、字段语义、可见性口径、权限范围、交互形态。判据：**答完之后方案里会多出一句业务规则吗？** 不会 → 降级为「给开发」备注。
- **不问答案早已确定的问题。** 建议默认 = 维持现状 / 不需要 / 照搬存量既有规则 / 被代码锁死的问题，问了也是零信息量 —— 还会让产品对整份文档的可信度打折。**但要把这类问题下面的真问题捞出来改写**（例：问"状态要不要复位"没价值，问"前置条件漏了入库状态"才有价值）。
- **同一主题最多一条；依赖型问题不单独问。** 留痕/审计/导出体现是一件事，不要拆成三条各占一个编号；能被另一条答案推导出来的（答了 A 就锁死 B）不单独成条。
- **每条问题必须能改写成方案里的一句话。** "产品答完这句，方案里要改成哪一句？" —— 改不出来，说明这条问的是实现而不是方案，不该占额度。
- **丢弃一条疑点 ≠ 把它从视野里抹掉。** 广度承诺要求"扫过的都有结论"。被剔除的疑点必须落到「排查范围」表的"确认不受影响"或"作用域外"里**留痕**，只是不占产品额度。
- **交付前必跑两道机器校验**：引用校验（`verify-citations.sh`）+ 自洽校验（`check-issue-list.sh`）。计数、编号、交叉引用这类错是读者一眼就发现的 —— 一处错就足以让产品怀疑整份文档。
- **不替产品做决策。** 只列可选解读 + 标注建议默认值，最终由产品**改方案**来定。决策权归属错了，澄清就变成了"开发替产品写需求"。
- **问题清单里不给技术方案。** 问题单讲"业务上这里该是什么"，不讲"建议这么改代码"。除非该技术选择直接影响业务语义（如过滤时机影响数据正确性）。
- **不把"方案写得不够细"直接上报为问题。** 先在代码里找到对应的具体事实锚点，找不到锚点的说明是表达问题，合并到术语表/规范里解决，不要占用产品澄清额度。
- **一个问题的澄清额度有限。** 问题单超过 ~25 条，产品不会逐条改方案。合并同类项、只留真正影响实现的。
- **广度要全量扫，不要只挑"我怀疑有问题的"。** 只给几个猜测性问题，产品会觉得你在找茬；把七个维度扫完、连"确定不受影响"的都列出来，产品才知道"我漏了什么"。**广度靠扫描保证，深度靠追问保证。**
- **不要用"新增的东西怎么实现"替代"存量功能要不要跟着改"。** 前者方案里通常已经写了，后者才是方案里没有的。
- **问题清单是只读的，不设"产品答复"环节。** 产品通过**改方案**回应，不在文档里填答复表。**没有答复表** —— 有它就会诱导产品逐条填，而填出来的答案没有落到方案里，等于没澄清。
- **方案无疑点就不出问题清单。** 硬造的问题单是噪音：产品分不清哪些是真缺陷、哪些是凑数，整份文档的可信度会被拉低。
- **实现方案必须具体到 AI 不用再问，但不产出完整代码。** 变更点、类名方法、表结构、验收标准要写全；完整实现类不写 —— 那还是代码。
- **不产出代码。** 本 skill 的终点是 Markdown 文档。

## 运行方式

```
/req-clarify                                              # 无参数 → 走 Stage -1 输入引导
/req-clarify <方案地址或路径> --repo-backend <后端路径> --repo-frontend <前端路径> \
             [--branch <分支> | --branch-backend <后端分支> --branch-frontend <前端分支>] [--out <产物目录>]
```

**无参数运行是默认路径**：先做**输入引导**（① 项目地址 → ③ 取证分支 → ② 方案地址），用 `AskUserQuestion` 逐项收齐并回显确认后才开始。路径**默认当前终端目录**，但要使用者点头才生效；分支**默认 master（该仓无则 main），两端分别算**，同样要确认。表单只渲染在对话里，**默认不落盘**。

带参数运行则跳过提问，参数直接作为初值（`--repo-backend` / `--repo-frontend` 视为已确认），**只问参数没覆盖到的项**，其余流程一致。
`--out` 省略时，产物默认写到当前目录下的 `req-clarify-out/`，实际落到 `<产物目录>/<方案名> 迭代/`（单夹，每轮覆盖）。

## 产物清单

```
<out>/                                       # = <当前终端目录>/req-clarify-out/
└── <方案名> 迭代/                           # 单夹，每轮覆盖（无轮次后缀）
    ├── 产品方案/                            # 上传的方案/原型原文件，保留原始文件名
    │   ├── xxxx 方案.md
    │   └── xxxx 原型.html
    ├── 问题清单.md                        # 方案疑点 + 方案遗漏 + 排查范围    ← ★仅当有疑点
    └── 实现方案.md                          # 变更点+类名方法+DDL+验收标准    ← ★仅当无疑点
```

**产物目录里只有这 3 个交付物。** 中间分析（事实抽取、覆盖矩阵、七维度扫描、检查器）全部在对话内完成，不落盘。代码基线快照落在缓存目录 `<基线根>/<repo名>/<分支>-<提交>/`（默认 `${TMPDIR:-/tmp}/req-clarify-baseline`），不进交付物、不进版本库。

**产品只读 `问题清单.md`（或 `实现方案.md`）。**

**`问题清单.md` 与 `实现方案.md` 二选一，不会同时存在。**

| 情形 | 交付什么 | 接下来谁做什么 |
|---|---|---|
| 方案**有**疑点 | `问题清单.md` | 产品**只读**问题清单 → 改方案 → 提交回来**复用同一夹**重跑（版本号 +1） |
| 方案**无**疑点 | `实现方案.md` | AI / 开发**照着直接编码**，不再提问 |

**`问题清单.md` 转给产品** —— 它必须自包含：产品不看其它文件也能读懂每个问题、看到证据、据此改方案。
**`实现方案.md` 转给编码代理** —— 它必须具体到不用再问任何问题（见「实现方案写作规范」）。

## 配套工具

**脚本路径**：本文件里所有 `<skill目录>/scripts/xxx.sh` 里的 `<skill目录>` = **本 SKILL.md 所在目录**，脚本在它的 `scripts/` 子目录下。装在用户级是 `~/.claude/skills/req-clarify/`，装在项目级是 `<项目>/.claude/skills/req-clarify/` —— **调用前先确认实际位置**，路径不对就手写等价命令，别因为找不到脚本就跳过这一步。

| 脚本 | 用途 |
|---|---|
| `scripts/scan-repos.sh` | **Stage -1 先跑这个**：扫描基准目录 + 一层子目录里的候选仓库，输出绝对路径、端归属（后端/前端/前后端/未判定）、当前分支、有无 master/main、有无提交、未提交数 —— 作引导「项目地址」时的预填依据，避免让使用者凭空想路径。`scan-repos.sh [基准目录]`，省略时取当前终端目录 |
| `scripts/prepare-baseline.sh` | **先跑这个**：锁定 master/main 分支、导出只读副本到基线根目录（默认 `${TMPDIR:-/tmp}/req-clarify-baseline`，**不在产物目录里**）、报告基线完整性与降级情形；按 `(repo, 分支, 提交)` 内容寻址自动复用；支持 `--label <后端\|前端>` 区分两端 |
| `scripts/survey.sh` | 机械定位六类代码事实的候选位置（`file:line` 线索）—— 传入**基线目录**（双仓各跑一次，`--label` 区分） |
| `scripts/verify-citations.sh` | 校验交付物里每处 `file:line` 引用是否真实存在、打印所指行内容并标注命中基线 —— `--baseline <dir> [--baseline <dir>] -- <文档...>`（双仓各传一个）。对 `问题清单.md` 或 `实现方案.md` 跑 |
| `scripts/check-issue-list.sh` | 校验 `问题清单.md` 的**内部自洽** —— 头部/正文/版本记录三处计数是否一致、Q 编号是否连续、排查范围表每行「需要改处数」是否等于「对应问题」条数、合计行是否等于各行之和、免打扰清单条数、Q/REQ 交叉引用、基线行是否写成 `路径@分支@提交`。传 `--baseline <槽位目录>`（可重复）时额外校验**文档里的提交号 = 真实基线槽位**（防凭记忆写错）。`check-issue-list.sh [--baseline <dir>]... <问题清单.md>` |

交付前自查：① `产品方案/` 含方案原文与原型原文件（原始文件名）② 两份交付物之一已落盘 ③ 每处 `file:line` 都过 `verify-citations.sh`（对两份基线跑）④ **G0/G1/G1b/G2/G3/G4/G5/G8 全绿** ⑤ `问题清单.md` 与 `实现方案.md` 只存在其一 ⑥ 若出 `实现方案.md`：G6/G7 全绿、零 `TBD`/`待确认` ⑦ **交付物头部都写了后端/前端两行基线分支与提交**（从 `prepare-baseline.sh` 的输出抄，不凭记忆写）⑧ 出 `问题清单.md` 时：**G9 全绿** —— `check-issue-list.sh` 零 FAIL。
